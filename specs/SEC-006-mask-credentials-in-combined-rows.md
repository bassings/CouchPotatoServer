# SEC-006: credentials in combined rows are masked on the settings read

Status: planned; owner decisions D1 to D12 recorded 2026-11-23. D12 ("Server
remembers removed rows") supersedes D2 and D7 and was written into this spec
after two lens review rounds; its criteria are marked and have had no lens
read. Ready for slicing once the choices listed under "Choices taken in the
D12 revision" are confirmed or overturned.
Follows SEC-004 (group save) and SEC-005 (Jackett key bound to its address);
queued by SEC-005 owner decision D3.

## Problem

`GET /api/<key>/settings` (`Settings.view` / `getValues`) returns the combined
options `newznab.api_key` and `torrentpotato.pass_key` in the clear. A combined
control cannot be typed `password`, so the masking every other credential gets
does not reach them (`tests/unit/test_settings_credential_masking.py` pins
both as unmasked today).

- `newznab.api_key` holds every Newznab indexer key, comma-joined.
- `torrentpotato.pass_key` holds each TorrentPotato row's pass key. After a
  Jackett sync that is the Jackett API key, copied into every synced row, so
  the key that `torrentpotato.jackett_api_key` masks is readable beside it.

Consequences measured or recorded so far:

- Every load of the Settings page and of the setup wizard puts every indexer
  key into the browser: the response body, the DOM, the browser cache, any
  saved HAR file, any screenshot.
- A holder of the CouchPotato API key reads all of them in one request.
- SEC-005 does not protect the Jackett key from that holder (SEC-005 gap (u)).

The fix cannot be masking alone. Measured at SEC-005 review round 1: with
today's `settings.save_group`, sending the displayed mask back overwrites the
stored key with the mask, an empty cell removes it, and a missing column is
refused. A masked read plus today's save would destroy stored keys on the
first unrelated edit. Masking and a save that can keep a stored credential
must ship together.

The cost of doing nothing: every load of the Settings page or the wizard keeps
copying every indexer key, and the Jackett key SEC-005 masks elsewhere, into
the response body, the browser cache and any HAR file or screenshot taken for
a bug report, so one shared capture discloses credentials that can only be
recovered by rotating the key at every indexer.

What this change does not make safe, stated here so nothing built from this
spec overclaims: a HAR file or saved page still contains the CouchPotato API
key, because it is in the URL of every API request the page makes, and that
key unlocks every indexer key to anyone who can reach the server. A capture
that includes a Show, or a key being typed, contains that indexer key as
well. A capture that includes the removal of a row contains a restore handle
(D12): it reveals no key, but with the API key from the same capture it can
put the removed row back until the handle is used or expires.

Threat model, one fact found at the review of this spec (measured
2026-11-23): the settings read was served as JSONP (`?callback_func=`) to a
page on any origin that knew the API key, so the whole read was readable
cross-origin, and after this change the token and every host would have
been. That was closed by a separate fix, now on `master` (D10, see
Dependencies). The rule it leaves for this design: the token must never
authorise anything on its own.

A second fact, found at the second review round (measured 2026-11-23 against
`master`): an origin listed in `cors_origins` passed both Origin checks this
design relies on by sending `X-Forwarded-Host` with its own host, so the
cross-origin refusal of D9 and the reveal gate did not hold against it. That
is fixed as its own change ahead of this spec (see Dependencies). Every
sentence here that says a listed origin is refused is true only with that fix
on `master`.

## Owner decision D1 (2026-11-23)

The full record of decisions D1 to D12 is under "Owner decisions" below.

"Dots with a Show button." A saved key is shown as dots on the Settings page;
a button fetches and shows the real key for that row.

Stated plainly, because it bounds what this spec can claim: with a Show
button, a holder of the CouchPotato API key can still read every indexer key,
one explicit request per key. This spec therefore does NOT stop that holder.
What it changes is that keys are no longer in the bulk settings read (and so
not in every page load, cache entry, HAR or screenshot), and that each reveal
is a separate, logged request. Decision D4 confirms the limit: the reveal route
is gated by the API key and the Origin check alone. Under D12 the Settings
page makes a reveal request only when Show is pressed: removing a row and
undoing a removal fetch no key.

## Proposal

As amended on 2026-11-23 to agree with the acceptance criteria and the owner
decisions, D12 included. Where this summary and a criterion differ, the
criterion governs.

1. **Declare which columns are credentials.** The `combined` option gains a
   `secret` list beside `combine` and `pairing` (`newznab`: `api_key`;
   `torrentpotato`: `pass_key`), and an `address` list naming the column a
   secret is sent to (`host` in both), which decision D3's log line needs
   (AC-SEC-18). One Settings method derives each from the registered options,
   as `combine_groups()` does (AC-ARCH-1).
2. **Mask on read.** `getValues` returns, for a secret column, a comma-joined
   value with one fixed mask per non-empty stored cell of that column and an
   empty string per empty cell. The count is that column's own stored cell
   count, not the padded row count, and the mask does not reveal a key's
   length (AC-QA-1). Applies to every reader of `getValues` (the settings API,
   the Settings page, the wizard).
3. **A freshness token.** The read also returns, per combine group, inside
   `combine_state[section]`, a token that is a keyed hash of every stored
   column of the group. The key is random per process and held in memory only,
   so a restart makes earlier tokens stale (AC-SEC-3, AC-ARCH-5, AC-OPS-11).
   Each group on the page uses the token issued with its own rows
   (AC-DATA-29).
4. **Keep-by-reference on save.** In `settings.save_group`, a secret cell is
   a string (a new value, validated as today), the object
   `{"keep": <row index at read time>}`, or the object
   `{"restore": <handle>}` of item 8. A save that contains any `keep` or
   `restore` must carry the token from the read it was built on; the server
   refuses it, and writes nothing, when the stored group no longer matches the
   token or the index is out of range. This reverses SEC-004 owner decision D5
   (no stale-save token) for saves that contain a `keep` or a `restore`, and
   only for those: a save of plain strings with no token behaves as on master
   (AC-SIMP-7). Any string containing the mask text is refused as a secret
   cell value, so a client that has not been updated cannot write dots over a
   key (AC-DATA-2). A `keep` is accepted on a row whose address changed, and
   logged (D3, AC-SEC-18). A save carrying any `keep` or `restore` is refused
   when the request is demonstrably from another origin, an origin listed in
   `cors_origins` included (D9, AC-SEC-21).
5. **Reveal.** One new route returns one secret cell (`section`, `column`,
   `row`, `token`) by POST with a JSON body, gated by the API key and the
   Origin check alone, as the Jackett routes are (D4), and logged at INFO with
   section, column and row only, never the value. `row` is the secret column's
   own cell index, so a reveal is answered on a misaligned group too (D11).
   Only Show uses it.
6. **Settings page.** A secret cell is a password field whose value is never
   the mask: the saved state is carried by the placeholder (AC-DESIGN-1). Each
   stored cell has one Show/Hide button, a 44 px target, labelled by column and
   row number and never by the row's name or host (AC-A11Y-1). Untouched cells
   are sent as `keep`, edited cells as the typed value; a cell typed into and
   then emptied counts as untouched (D8). The Jackett sync keeps working: a
   merge sync builds its rows server-side and is unaffected by masking. The
   page has no reorder control: the only page action that changes a row's
   position is Undo, which re-inserts a row at its own index, or appends it
   after a re-read (AC-DATA-21). Remove makes no request and the page holds no
   stored key for Undo (D12, AC-SEC-20). Undo before the removal has been sent
   is client-side, as on master. Undo after the removal has saved sends the
   handle the server returned for that row as a `restore` cell (AC-DATA-18).
   If that save is refused because the group changed elsewhere, nothing is
   lost: the server still holds the row, and after the reload the page still
   offers Undo for it, which appends it (AC-DATA-21). On a misaligned group
   the page sends each stored key as shown or typed text and holds the save
   until it can, and Remove is not offered for a row holding a stored key
   until the group is repaired (D11, AC-DATA-25).
7. **Wizard.** The wizard masks saved keys and keeps them with `keep`. It has
   no Show button and makes no reveal call (D5). Its Remove has no Undo
   (measured: `removeIndexer` in `wizard.html` splices the entry and nothing is
   written until Continue). The server's rule of item 8 does not ask who sent
   the save, so the keys of rows the wizard removes are held too; the wizard
   ignores the handles and offers no restore.
8. **The server remembers removed rows (D12).** When a token-carrying
   `settings.save_group` is accepted, every stored secret cell that was
   non-empty and that no `keep` in the save named is kept in an in-memory
   hold, and the reply returns an opaque random handle for each (AC-DATA-30).
   A later save may place `{"restore": <handle>}` in a secret cell of the same
   section and column: the server substitutes the held text, validates and
   writes like any other save, and drops the entry (AC-DATA-31). Entries live
   in process memory only, for at most 24 hours, within a fixed bound, and are
   gone on restart (AC-SEC-23, AC-SEC-25, AC-DATA-28). A stale refusal lists
   the handles of the rows removed by the save that replaced the state the
   caller built on, so a page whose removal landed but whose reply was lost
   can still restore the row.

## Dependencies

Both must be on `master` before P1 of this spec merges (hard constraint 4).
This spec specifies neither fix. It asserts the effect of each, so a
regression of either fails here too.

- **The JSONP fix on the settings read (D10).** `callback_func` on the
  `settings` route is refused. Merged to `master` as #630 (`dd80c7574`,
  `specs/FIX-2026-11-23-settings-jsonp-refused.md`), verified 2026-11-23 by
  `git merge-base --is-ancestor`. P1 puts the freshness token into the
  settings read, which is why it had to land first. Asserted by AC-SEC-1.
- **`X-Forwarded-Host` cannot vouch for an origin on the CORS allow-list.**
  A separate spec and change
  (`specs/FIX-2026-11-23-origin-check-allow-listed-forwarded-host.md`, branch
  `fix/origin-check-allow-listed-xfh`), not on `master` when this was written.
  Without it an origin listed in `cors_origins` passes `_cross_origin_post`
  and `_cross_origin_guarded_route` by sending the header with its own host,
  which defeats the cross-origin refusal of a `keep` or `restore` (D9,
  AC-SEC-21) and the reveal gate (AC-SEC-6), and makes the reasoning of
  AC-SEC-18 and the doc text of AC-OPS-15 false for that origin. P1 ships
  that doc text in a beta, so the fix is a prerequisite of P1, not of P2.
  Asserted here by case (f) of AC-SEC-21 and by the forwarded-host case of
  AC-SEC-6.

## Not in scope

- Masking `core.api_key` (deliberately readable; see
  `test_settings_credential_masking.py`).
- Encrypting credentials at rest in `config.ini`.
- The outbound-proxy gap (SEC-005 gap (j); owner decision 2026-11-23: left
  documented).
- Storing each indexer as one record instead of parallel lists.
- Combined groups with no secret column. The three automation URL groups
  (`imdb`, `itunes` and `letterboxd`, columns `automation_urls_use` and
  `automation_urls`) and any other combined group that declares no `secret`
  column are untouched: their values are not masked, they have no Show
  button, no `keep`, no `restore`, no hold and no reveal, and their saves are
  accepted exactly as on master, with no token sent by the page and none
  required (AC-SIMP-7). The only thing they gain is an exemption entry in the
  sweep of AC-SEC-13.
- A Show button, a reveal call, Undo or a restore in the setup wizard (D5).
- A control to reorder rows. Neither page has one today and this change adds
  none; reorder by `keep` is a server capability, tested on the server.
- The JSONP fix and the forwarded-host fix themselves (Dependencies), and
  JSONP on any route other than `settings` (D10).
- `keep`, `restore` and holding on a misaligned group (D11, D12: all three
  stay refused or absent there).
- A login-session requirement on the reveal route (D4).
- The freshness token on saves that carry no `keep` or `restore` (vetoed at
  planning; SEC-004 gap 4 stays open for those).
- A route to list, read, extend or delete held rows, and any way to restore a
  removed row after a restart or after 24 hours (D12).
- Holding rows removed by a token-less save or by a Jackett sync, merge or
  replace (AC-DATA-30).
- More than one live Undo per group, and an Undo for a key replaced by typing.
  The hold keeps a replaced key because it cannot tell replacing from
  removing (AC-SEC-25); the pages offer nothing for it.
- A way to dismiss a restorable line before its 24 hours end (AC-A11Y-19).
- The page fetching or holding a stored key for Remove or Undo, and the
  put-back control (D2 and D7, superseded by D12).

### Choices taken in the D12 revision

D12 fixed the frame (the server remembers removed rows; the page holds no
key). The points below were not decided by the owner. Each is the course this
revision took, with the alternative it rejected and why. Each can be
overturned before P1 is built without touching the frame.

| | Choice taken | Alternative rejected, and why |
|---|---|---|
| C1 | **Which rows are held is decided by `keep` indexes alone** (AC-DATA-30): a non-empty stored secret cell that no `keep` names is held. | D12 as put to the owner said "whose non-secret cells do not appear". Matching rows by their contents loses a key when two rows have the same non-secret cells and different keys (two accounts at one indexer), which is the mispairing class this design exists to end. The cost of the choice: a key replaced by typing is held too, for up to 24 hours. A third course, the page naming the rows to hold in the request, was rejected because a client path that forgot to name one would lose a key silently. |
| C2 | **An entry holds the secret cell and the row's address cells only**, not every column (AC-DATA-30). | Holding the whole row. The page already has the non-secret cells and shows them; a second copy on the server is a second thing to mispair, and the address is all the D3 log line needs. |
| C3 | **A save with no token, and a builder save (the Jackett sync), hold nothing** (AC-DATA-30). | "Any accepted save that omits stored rows holds them." A token-less save names no stored row, so every key would count as omitted on every such save and would evict real entries. Its senders either hold the cells as text (an old page) or offer no Undo (a script). |
| C4 | **A stale refusal lists the handles of rows removed by the save that replaced the caller's state** (AC-DATA-31). | Returning handles only in the reply to the removing save: when that reply is lost the page has no handle and the row cannot be restored, which is the first Critical of review round one again. Putting handles in the settings read was rejected because it would put them in every page load. |
| C5 | **Entries expire 24 hours after they are made** (AC-SEC-25). | No expiry: a removed or replaced key would then sit in the memory of a server that runs for months. 24 hours is above the 20-hour exception of WCAG 2.2.1, and the page says so when it happens (AC-A11Y-21). An idle expiry was rejected: nothing touches an entry between its making and its restore, so idle and age are the same thing. |
| C6 | **Bound: 64 entries per section, 256 in all; at the bound the oldest is evicted and the save is never refused** (AC-DATA-28). | Refusing the save at the bound. With C1 a key replacement makes an entry, so a refusal would stop ordinary edits with no remedy but a restart. Eviction can cost an Undo only after 64 later entries in one section within 24 hours; the page that caused it is told in the reply (`dropped`), and any other page is told when Undo is pressed. |
| C7 | **A Jackett sync, merge or `replace=true`, keeps the section's entries** (AC-DATA-28). | Clearing them on a replace. Keeping is the safe direction and a later restore is an ordinary token-checked save. |
| C8 | **Positioning: Undo re-inserts at the row's own index while the rows on screen are the ones it was removed from; after any re-read that replaced the rows it appends** (AC-DATA-21). | Re-inserting at the old index after a re-read: the index describes rows that no longer exist. |
| C9 | **On a misaligned group, Remove is not offered for a row holding a stored key until the group is repaired** (AC-DATA-25). | Offering Remove and withdrawing Undo once the removal is sent, as the D12 brief allowed. The removal is sent 8 seconds after the press, so Undo would become an 8-second control, against AC-A11Y-18 and WCAG 2.2.1. The repair save is always available first and loses nothing. |
| C10 | **The page keeps one live Undo per group, as on master; a row whose Undo was pressed, and any removal the page holds a handle for, survives a re-read as its own restorable line, one line per row** (AC-DATA-20, AC-DATA-21). | A single slot for restorable rows (lens-data F3 of round two: a second arrival would drop the first), and an Undo list for every removal ever made (a larger change to the page than D12 asks for). |
| C11 | **One refusal reason, `restore_unknown`, for a handle that was never issued, was used, expired, was evicted or belongs to another section or column, and it is checked before the token** (AC-SEC-24, AC-DATA-31). | Separate reasons: they would let a caller learn which of those a handle is, and the page needs only "cannot be restored". Checking the token first was rejected because a restore that landed with its reply lost would then look like an ordinary stale refusal. |
| C12 | **A restore beside a changed address logs its own fixed INFO line** (AC-DATA-33), and a restore's row is named by its position in the saved group. | Reusing the kept-on-a-changed-address line unchanged: that line names a read-time row index, which a restored row does not have. |

Still open (none blocks slicing; each names where it must be settled):

- **The `address` declaration (D3).** AC-SEC-18 needs to know which column a
  secret is sent to, and AC-ARCH-1 forbids naming a column in `settings.py`.
  This spec adds an `address` list to the combined option for it. That
  declaration was written after the planning cycle and was not examined by
  lens-architecture or lens-simplicity; the alternative (log on a change to
  any non-secret pairing column) was rejected here because `use` is a pairing
  column in both groups, so switching a row off would be logged as an address
  change. D12 gives the declaration a second use (the address recorded in a
  held entry, AC-DATA-33). To be confirmed in the P1 slice review.
- **D12 has had no lens read.** Every criterion marked "owner decision D12"
  was written after the second review round. lens-simplicity in particular
  has not seen the hold: it is new server state, which the planning cycle
  avoided (AC-OPS-8 as first written). The P1 slice review is its first read,
  and the reviewer is told so.
- **Undo, then leaving the page before the restoring save is answered.** A
  refusal of the leave flush is seen by nobody; the row stays removed and its
  key stays in the hold with no page knowing the handle (AC-DATA-18). Recorded
  as a limit. Closing it would need handles in the settings read (rejected in
  C4).
- **How long timers survive in a background tab.** The page withdraws an
  Undo at 24 hours by its own clock (AC-A11Y-21); a throttled or suspended tab
  may run that late. Not measured. The design is safe either way: a late
  press is refused as `restore_unknown` and says so.

### Security (lens-security)

- **AC-SEC-1:** With three Newznab rows holding distinct keys and two TorrentPotato rows (one holding a Jackett key after a sync), the raw body of `GET /api/<key>/settings` contains none of those key strings, in plain, JSON-escaped or URL-encoded form, and the Jackett key appears nowhere in it. Proof: integration, a real HTTP request and a search of the raw response bytes. The settings read is also requested as `GET /api/<key>/settings?callback_func=x` with a foreign Origin header: that request is refused (the D10 fix, whose status and body are that fix's to state), and the raw response, whatever its content type, contains none of those keys in plain or Python `repr`-escaped form, no host of any row and no freshness token. A regression of the D10 fix therefore fails this test. Proof adds: one more real request, with the fixture including a key whose `repr` form differs from its JSON form (a quote and a backslash). *(amended 2026-11-23, owner decision D10)*
- **AC-SEC-3:** The freshness token is keyed, and its key is random per process and held in memory only: two Settings instances holding byte-identical stored groups but different token keys produce different tokens, the token never equals an unkeyed hash (SHA-256, SHA-1 or MD5) of the stored columns joined in any order, and the token key appears in no API response and no log line. Proof: unit. The MAC input is an unambiguous encoding of the section name, each column name and each column's stored text (for example a JSON array of name and text pairs), not the texts joined: two groups whose stored columns are byte-identical produce different tokens, and two states that split the same text differently across columns produce different tokens. A submitted token is compared with `hmac.compare_digest`. Proof adds: unit for both collisions, and a code read for the comparison. *(amended 2026-11-23, lens-security review of the amendment)*
- **AC-SEC-4:** The reveal route returns a value only for a (section, column) pair where the column is in a registered combined option's declared `secret` list. Requests naming `core.password`, `core.api_key`, a core session secret option, `torrentpotato.jackett_api_key`, any non-combined `password` typed option, a non-secret column of a combine group (for example `newznab.host`), a column of the other group, a hidden or non-readable option, or an unregistered section each return a refusal carrying no stored value. Proof: integration, one real HTTP request per pair. (Merges part of AC-QA-10.)
- **AC-SEC-5:** The reveal route refuses, with no value in the body, a row given as JSON true, false, -1, "0", 1.5, null, a list, an object, or an integer equal to or beyond the named secret column's own stored cell count (D11: `row` is that column's cell index, which on an aligned group is the row index); JSON true does not return row 1 and -1 does not return the last row. Proof: integration. (Merges part of AC-QA-10.) *(amended 2026-11-23, orchestrator decision D11)*
- **AC-SEC-6:** The reveal route refuses, with no value in the body and no key in any log record: a request with no API key or a wrong one (401); a request whose Origin or Referer is another origin, or with neither header (403); a GET; a POST whose content type is not `application/json`; a POST carrying any query parameter other than `t`; a body with a missing or extra top-level key; a missing token; a token from before the group last changed. - **AC-DATA-18:** What Undo sends is decided when the payload is built, by the one order of AC-DATA-32, from what the page knows about the row (D12). (i) No save carrying the removal has been sent: the store still holds the row; it returns in the state it had, and where nothing else was unsaved no save is sent at all (AC-QA-15). (ii) A save carrying the removal was accepted and its reply listed the row in `held`: the row returns carrying that handle and no origin index, and its cell is sent as `{"restore": <handle>}`, with a `keep` of its current origin index for every other stored cell and the group's token. (iii) A save carrying the removal was sent and no reply has yet said what became of it (it is still open, it failed on the network, or it was refused): the row returns keeping its origin index and is sent as a `keep` of it under the group's unchanged token. If the removal never landed, that save is accepted and nothing was ever lost. If it landed, the token is stale, the save is refused with nothing written, and the refusal lists the row's handle (AC-DATA-31), which the page adopts (AC-DATA-27); the message of AC-DESIGN-7 is shown, and after Reload the row is restorable (AC-DATA-21). (iv) A reply that arrives after Undo is applied by the same rule: an accepted removal save that lists the row turns the returned row's cell from `keep` into `restore` before the next payload is built. A non-empty value typed into the cell wins over all four. When the restoring save is accepted the cell becomes a `keep` of its new position. When it is refused or fails, the row stays on screen under the group's ordinary unsaved or error state, never presented as saved, and keeps its handle for the next attempt: the server's entry is consumed only by an accepted save. One case remains and is recorded in `docs/technical-debt.md` beside limit (b) of the 8-second entry: Undo pressed, and the page left before the restoring save was answered. The leave flush sends the restore; a refusal of it is seen by nobody; the row then stays removed, and its key stays in the hold, which no page can reach, until the entry expires. Proof: UI unit on the payload builder for each state, plus parts (b), (d) and (e) of AC-QA-22 and part (a) of AC-QA-26. *(rewritten 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-19:** Ordering (D12). (i) The `REMOVAL_UNDO_WINDOW_MS` delay is counted from the press, as on master: Remove makes no request, so nothing delays the row leaving the screen or shortens the window. (ii) A save of the same group pending or in flight at the press is not disturbed by Remove; the removal goes in the next payload, as on master. (iii) When the removal save is accepted, `held` is applied first, by each row's origin index as it stood when that save was built, and only then are the token and the origin indexes re-based as AC-DATA-7 states; a handle is never matched by position (AC-DATA-27). (iv) `pagehide`: `flushGroupsOnLeave` sends each waiting group's payload with `keepalive` and that group's own token (AC-OPS-3), built by the same pure function, so a `restore` still waiting out its debounce leaves as a `restore`. Nothing is dropped or withdrawn at `pagehide`: the page holds no key to drop. (v) `pageshow` with `persisted` needs no handling of its own: whatever the leave flush did, the page's next save is either accepted or refused as stale, and the stale path of AC-DATA-18 (iii) recovers a removed row's handle. The debt entry "A removed Settings row waits 8 seconds before it is saved" is updated for this (AC-OPS-12): an Undo after a back/forward-cache restore no longer overwrites what the leave flush wrote; it is refused as stale and the row is then restorable. Proof: UI unit with a controlled clock for (i), (iii) and (iv); part (i) of AC-QA-22 for (v). *(rewritten 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-20:** The page offers one live Undo per group at a time, as today (`group.removal` is a single slot): a second Remove in the group replaces the offer, and an edit, an added row or a button-action lock withdraws it, exactly as on master and by the user's own action. None of that touches the server's entries: each removed row's secret cell is its own entry with its own handle (AC-DATA-28). Removing several rows in sequence leaves `config.ini`, after the save, holding exactly the remaining rows with their own keys, and never a key from a removed row under a surviving host. A row the user pressed Undo for is never displaced by a later removal: once returned it is a row on screen, and if a re-read replaces the rows before it is saved it becomes its own restorable line (AC-DATA-21). Proof: part (g) of AC-QA-22; UI unit and E2E that two rows returned by Undo and then caught by one re-read give two restorable lines, and that after both are restored `config.ini` holds both keys beside their own hosts (lens-data F3 of round two). *(rewritten 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-21:** A removed row survives a refused restore and a re-read (D12, superseding D7). When a re-read replaces the rows of a group (in practice the Reload that follows a stale refusal, and equally any other re-read that replaces that group's rows), every removed row the page holds a handle for, whether a row returned by Undo and not yet saved or the live removal, becomes a restorable line (AC-A11Y-19): the page keeps the handle, the row's number and its non-secret cells as they were when it was removed, not as edited since (AC-DATA-33). A removed row the page holds no handle for is dropped from the page's state by the re-read, as on master. That is how the page knows not to offer a restore for a row the store still holds: a handle exists only if an accepted save omitted the row (a reply's `held`, or a stale refusal's, AC-DATA-31), so where the removal never landed there is no handle, the re-read rows show the row, and nothing is offered. There is therefore no duplicate-row case. Positioning, one rule: Undo re-inserts a row at its own index only while the rows on screen are the ones it was removed from; after any re-read that replaced the rows, Undo appends it as a new last row. The page never matches a removed row against the re-read rows by host or any other cell and never writes into another row. The appended row carries the removal-time cells, `{"restore": <handle>}` and no origin index, and saves through the ordinary save with the re-read token and a `keep` for every other stored cell. If that save is itself refused as stale, the same path repeats and the entry is still held. Recorded limits, in `docs/technical-debt.md`: a restorable line is offered until its entry expires (24 hours), the server restarts or the page is left, and has no control to dismiss it sooner; and the leave-flush case of AC-DATA-18. Proof: parts (a) to (c) of AC-QA-26, plus UI unit that the appended row is last and that no other row's cells changed. *(rewritten 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-22:** An emptied secret cell changes nothing (D8). On the Settings page and in the wizard, a secret cell the read marked non-empty whose edited value is empty (typed into and erased, or cleared, with or without surrounding whitespace) is treated as untouched: it is sent as a `keep` of its origin index, it shows the saved rest state, and Remove treats it as stored (AC-DATA-17). No save either client builds contains an empty string for a cell the read marked non-empty. A stored key is cleared only by removing its row or typing a replacement. A cell with no stored key (an added row, or a cell the read returned empty) that is empty is still sent as an empty string, as today. A row returned by Undo is not such a cell while it carries a handle or an origin index: emptied, its cell is sent as its `restore` or its `keep` (AC-DATA-32). The server is unchanged by this: an all-string save from a script may still store an empty cell (AC-SIMP-7). Proof: UI unit on the pure function of AC-ARCH-10 for each case, plus part (d) of AC-QA-26. *(added after the planning cycle, owner decision D8; not lens-reviewed at planning)* *(amended 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-25:** A misaligned group that holds keys can be repaired without retyping or losing one (D11). The server answers a reveal on a misaligned group by the secret column's own cell index (AC-QA-13) and still refuses any `keep` there (AC-DATA-6). On a group the read marks misaligned, the Settings page therefore never sends `keep`: for each secret cell the read marked non-empty it sends the text currently shown by Show, or the non-empty text the user typed, and while any such cell on the rows it would send is neither shown nor retyped it sends no save at all, for an edit, a removal or the leave flush alike, and shows the message of AC-A11Y-20. It never sends an empty string for such a cell (D8 applies: an emptied cell is untouched, and here that means it blocks). A key counts as shown only while it is shown: Hide returns the cell to blocking and the page keeps no copy. The save it does send carries every cell as a string and the page's token, so it is refused, with nothing written, if the group changed elsewhere since the read. When it is accepted the group is aligned, every secret cell becomes a `keep` of its saved position (AC-DATA-7) and the shown keys leave the DOM (AC-DESIGN-5). Nothing is held from a save of a misaligned group (AC-DATA-30), and a `restore` is refused there as a `keep` is (AC-SEC-24), so a keyed row removed from one could not be restored once the removal had saved; withdrawing Undo when the removal is sent would turn Undo into an 8-second control (AC-A11Y-18). On a misaligned group, therefore, Remove is not offered for a row whose secret cell holds a stored key the user has not replaced, shown or not (AC-A11Y-20). Remove works as on master for a row with no stored key (an added row, a padded row, a cell the read returned empty) and for a row whose key cell holds a typed replacement, because everything Undo would return is then the user's own text on the page; its delayed save is subject to the same block. Once the repair save is accepted the group is aligned, and Remove and Undo are those of every other group. No entry can exist for a group that is still misaligned (none is made there, and `settings.save_group` only ever writes aligned groups), so the page never shows a restorable line on one. In both shipped groups the secret column is a pairing column, so it never holds a cell beyond the row count and no stored key is outside the rows the page shows; the sweep of AC-SEC-13 fails for a `secret` column that is not in `pairing`. The wizard is unchanged: it writes nothing for a misaligned group, and its pointer ("Fix the rows in Settings, under Searchers, then Newznab") now leads to this repair. Proof: parts (e) and (f) of AC-QA-26, plus UI unit on the pure function for a misaligned group. *(added after the planning cycle, orchestrator decision D11; not lens-reviewed at planning)* *(the Remove rule rewritten 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-26:** *(withdrawn 2026-11-23, superseded by owner decision D12)* The page holds no key that a save could leave without. What a returned row is sent as is AC-DATA-32.
- **AC-DATA-27:** A row returned by Undo carries exactly one of: its origin index (the store is taken still to hold it), a handle (an accepted save omitted it), or neither (it had no stored key). The page moves a row from the first to the second only on the server's word, and by the origin index as it stood when the save was built, never by position: when an accepted save's reply lists that index in `held`, or a stale refusal does (AC-DATA-31), the row, whether it is back on screen after an Undo or is still the live removal, takes the handle and loses its origin index in the same step, before the reply's re-base of the other rows is applied. When an accepted save that omitted the row does not list it, the row loses its origin index and has neither: if the read marked its secret cell empty that is correct, and the cell is sent as an empty string; if the read marked it non-empty, the server no longer holds that key (it was evicted within the same save, AC-DATA-28), and the row is treated exactly as after `restore_unknown`: it shows the text of AC-A11Y-17 and its cell is an added-row cell. Both replies are applied to the removed row whether or not the group was edited after the save was built (today `sendGroup` discards a refusal for rows that have since changed; the `held` list is read before that test). Apart from a stale refusal's `held`, a refused or failed save changes no row's origin index or handle. A row carrying a handle keeps it through being removed again and returned again, through edits to any of its cells, and through refused or failed saves; it gives it up only when a save that includes the row is accepted (the cell becomes a `keep` of its saved position) or when the server answers `restore_unknown`. Proof: UI unit for each transition; parts (d), (e) and (f) of AC-QA-22; mutations (3), (4) and (5) of AC-QA-23. *(added 2026-11-23, lens-data review of round two, F1 and F5, restated for owner decision D12; not lens-reviewed)*
- **AC-DATA-28:** No entry is dropped because another arrives (D12). Each held secret cell is its own entry with its own handle, and making, restoring or refusing one entry changes no other. The hold is bounded: at most 64 entries for one section and 256 in all, two module-level constants. When making an entry would pass a bound, the oldest entry of that section (at the overall bound, the oldest entry of any section) is evicted first. The save is never refused for the bound: a refusal would stop every edit of the group, with no remedy but a restart. The reply to the save that caused an eviction lists each evicted handle in `dropped`, and its `held` lists only entries still live when the reply is built, so the page that caused it withdraws any Undo it shows for an evicted row and says so (AC-A11Y-21); a page that did not make that save learns when Undo is pressed, by `restore_unknown` (AC-A11Y-17). Recorded limit, in `docs/technical-debt.md`: an Undo can be lost to the bound only after 64 later removals or key replacements in the same section within 24 hours. A Jackett sync, merge or `replace=true`, neither makes nor removes an entry: keeping them is the safe direction, and a restore afterwards is an ordinary token-checked save (AC-QA-12). Proof: parts (g) and (h) of AC-QA-28. *(added 2026-11-23, lens-data review of round two, F3, restated for owner decision D12; not lens-reviewed)*
- **AC-DATA-29:** Each group holds the token issued with its rows: from the read that derived them, from a re-read that replaced them, or from the reply to a save of them. A re-read that does not replace a group's rows (the re-read at the end of another section's button action, or `init()` run again while the group has unsaved rows) leaves that group's token, misaligned flag, row count and origin indexes unchanged. `fetchSettings` may go on replacing `combineState` wholesale, but nothing a save, a `keep`, a `restore`, a reveal or the keep-or-string choice of D11 uses is read from `combineState` after the group's rows were derived. Wherever this spec says a save carries "the group's token", this is the token meant; no criterion means the newest token the page has seen. - **AC-DATA-30:** What the server holds (D12). When a `settings.save_group` that was submitted as rows (not a builder) and carried a token is accepted and written, every stored secret cell that was non-empty before the write, and whose row index no `keep` in that save named, is put in the removed-rows hold as one entry: the section, the secret column, the cell's text exactly as `_stored_text` yields it (whitespace preserved, a legacy wrapper stripped as `get()` strips it), the row's index before the write, the text of that row's `address` cells before the write, the token the save carried, and the time. The rule reads `keep` indexes and nothing else. It never decides whether a row survived by comparing hosts, names or any other cell: two rows with the same non-secret cells and different keys would then lose a key (part (f) of AC-QA-28). Its consequences are accepted and stated: a stored key that was replaced by a typed value is held as well as a removed one (AC-SEC-25), and the keys of rows the wizard removes are held although the wizard offers no restore. No entry is made by: a save that is refused, or whose write fails (an entry is made only after `_write_group` has returned, in the same hold of the lock); a save with no token, which is the master path and names no stored row (AC-SIMP-7); a builder save such as the Jackett sync; a save of a group that is misaligned before the write, where a row index is ambiguous (AC-DATA-6); an empty stored cell. The reply to an accepted token-carrying save carries, beside the fresh token, `held`, one object `{row, column, handle, expires_in}` for each entry this save made that is still live, where `row` is the index before the write and `expires_in` is in seconds, and `dropped` (AC-DATA-28). Both are lists, empty when there is nothing to report. Proof: parts (a) to (f) of AC-QA-28. *(added 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-31:** What a `restore` does (D12). In `_save_group`, under the one hold of the lock: each `{"restore": <handle>}` cell is checked against the hold first, so a handle the hold does not have for this section and column refuses the save as `restore_unknown` whatever the token says (AC-SEC-24); then the token is checked as for a `keep`; then the entry's text is substituted for the cell, and the rows are validated by `_group_problems` and written like any other save. The entry is dropped only after `_write_group` has returned: a save refused for any reason, or whose write fails, leaves every entry it named restorable. The stored text is the entry's, byte for byte; the row's other cells and its position are whatever the save submitted (AC-DATA-33). Each restored cell logs one INFO line (AC-OPS-16). A stale refusal carries one thing more than today: `held`, listing `{row, column, handle, expires_in}` for each live entry of that section whose recorded token equals the token the refused save carried (compared with `hmac.compare_digest`), that is, for the cells omitted by the one accepted save that replaced the state the caller built on. This is how a page whose removal landed, but whose reply was lost, recovers the handle (AC-DATA-18 (iii)). The list is empty when that state was replaced by any other write; it is present on no other refusal and never in the settings read. Proof: parts (a), (e), (j) and (l) of AC-QA-28, and part (a) of AC-QA-26. *(added 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-DATA-32:** One order of precedence decides what a secret cell is sent as. It lives in the pure function of AC-ARCH-10 and applies to the debounced save, the forced flush and `flushGroupsOnLeave` alike: (1) a non-empty typed value, as a string; else (2) the row's handle, as `{"restore": <handle>}`; else (3) a valid origin index, as `{"keep": <index>}`; else (4) an empty string, only for a cell that has no stored key and no handle (a row added on this page, a cell the read returned empty, a row whose restore the server refused as `restore_unknown` or whose entry the server reported gone, AC-DATA-27); else (5) cannot be built: nothing is sent for the group, and it shows its error state with the row marked. Result (5) arises on a misaligned group, for a stored cell that is neither shown nor retyped (AC-DATA-25), where (3) is never returned and the text shown by Show counts as (1); and it is the result for any state the function does not recognise, so an unforeseen state blocks the save and never sends an empty string. An emptied cell is not a typed value (D8), so it falls to (2) or (3), and never to (4) while the row has a handle or an origin index. Show follows the same order: it sends a reveal only for a cell whose result would be (3) on a row the store is known to hold, and toggles the typed text for (1) (AC-SEC-22). Proof: UI unit over the table of states, including a row returned by Undo with a handle whose cell was typed into and then emptied (result 2, not 4); the restored-row case of part (d) of AC-QA-26; mutation (6) of AC-QA-23. *(added 2026-11-23, lens-data review of round two, F2, restated for owner decision D12; not lens-reviewed)*
- **AC-DATA-33:** A restored row's non-secret cells are the page's, and a changed address is logged (D12). The server substitutes the secret cell only: the hold supplies no other cell. On the page, Undo returns the row with the non-secret cells it had when it was removed, and the user may then edit them like any row's. If a re-read replaces the rows first, the restorable line keeps the cells as they were when the row was removed, not as edited after Undo, so Reload discards those edits as D6 says it discards every unsaved value. When an accepted save restores an entry beside `address` cells whose text differs, by the exact comparison of AC-SEC-18 (no trimming, case folding or URL normalisation), from the address text recorded in the entry, the server logs exactly one INFO line saying that a removed secret was restored on a row whose address changed, naming the section, the secret column and the row's position in the saved group and nothing else: no key, no handle, no old or new address, no row name. A restore beside the unchanged address logs only the restore line of AC-OPS-16. Proof: unit: a restore with the host unchanged (no such line), changed, changed only in letter case, and changed only by a trailing space (one line each), with caplog at DEBUG showing no host, key or handle in any record; UI unit that edits a returned row's host before the stale refusal and asserts the restorable line's row carries the original host. The page holds no stored key in any of these (AC-SEC-20). The wizard calls the same pure function and never reaches the `restore` result: `removeIndexer` has no Undo, nothing is written until Continue, and the wizard ignores `held` and `dropped` in the reply. On the server, D12 adds one cell form to `settings.save_group`, two lists to its reply, one list to its stale refusal, one refusal reason, and the hold of AC-ARCH-15; it adds no route and no request parameter (AC-SIMP-3). Proof: code read plus UI unit. *(rewritten 2026-11-23, owner decision D12; not lens-reviewed)*
- **AC-ARCH-15:** The removed-rows hold is one small object owned by `Settings`, created in its constructor and defined in `couchpotato/core/settings.py`: an insertion-ordered mapping from handle to entry, with the operations D12 needs (add the entries of an accepted save, take the entries a save restores, list the entries recorded against a token, evict and expire) and no others. No new module, no new dependency, no thread and no timer. Every read and write of it happens inside `_save_group`, under the `_PASSWORD_SAVE_LOCK` hold that already covers the token check and the group write; no other method of `Settings`, no provider and no route handler touches it, and `save_group_view` only relays the reply. It belongs to one `Settings` instance and ends with it, so it shares the life of the token key (AC-ARCH-5). Entries are made and dropped only after `_write_group` has returned, so a refused save, a failed write, and the interrupt window `save_group` documents (the disk written and memory rolled back) leave the hold as it was, which errs towards keeping an entry. Its two bounds and its lifetime are module-level constants beside the mask constant. Which columns it applies to comes from the `secret` and `address` declarations (AC-ARCH-1): no section or column name is added to `settings.py` for it. The clock it reads is one function, so a test advances it without patching `time` for the module. Proof: code read, plus the unit test of AC-ARCH-2 as extended. *(added 2026-11-23, owner decision D12; not lens-reviewed)*

## Slices

A proposed build order of independently reviewable PRs. Each slice is built
through `/tdd-task`, reviewed on its own diff, and leaves `master` releasable,
because every commit on `master` publishes a beta.

**Hard constraints.**

1. Masking on read must never ship without the save that can keep a stored
   credential: the PR that turns masking on either contains that save or lands
   on a `master` that already has it.
2. No PR that makes the read mask a secret cell may land unless the Settings
   page and the wizard on that `master` have each passed the masked-read E2E of
   AC-QA-27. This follows from the code as it is today: both clients send back
   the cells they read (`groupPayloadRows`, `newznabRowForEntry`), so a masked
   read in front of an unchanged client makes every save of those two groups a
   refused save (no key is lost, AC-DATA-2, but the group cannot be edited).
   Masking is therefore the last behaviour switched on, in P5.
3. A slice that changes a security property updates every document asserting
   the old property in the same PR (AC-OPS-15 is the first use of this rule).
4. Both prerequisite fixes are on `master` before P1 merges (see
   Dependencies): the D10 fix, which is (#630), and the forwarded-host fix,
   which was not when this was written.
5. D11's reveal rule is built in P2 as written here. It is not left to P3.
6. The removed-rows hold and `restore` are server work and are built in P1,
   with the save they belong to. P3 builds no server code. Until P3 lands no
   client sends a token, so nothing is held and no beta behaves differently
   for it.

If the slices are merged differently, P1 and P5 fold together and P3 and P4
must be in the same PR as them; the constraints do not move.
