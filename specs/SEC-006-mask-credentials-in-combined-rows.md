# SEC-006: credentials in combined rows are masked on the settings read

Status: planned; owner decisions recorded 2026-11-23; ready for slicing.
Follows SEC-004 (group save) and SEC-005 (Jackett key bound to its address);
queued by SEC-005 owner decision D3.

## Problem

`GET /api/<key>/settings` (`Settings.view` / `getValues`) returns the combined
options `newznab.api_key` and `torrentpotato.pass_key` in the clear. A combined
control cannot be typed `password`, so the masking every other credential gets
does not reach them (`tests/unit/test_settings_credential_masking.py` pins
both as unmasked today).

- `newznab.api_key` holds every Newznab indexer key, comma-joined.
- `torrentpotato.pass_key` holds each TorrentPotato row's pass key. After a
  Jackett sync that is the Jackett API key, copied into every synced row, so
  the key that `torrentpotato.jackett_api_key` masks is readable beside it.

Consequences measured or recorded so far:

- Every load of the Settings page and of the setup wizard puts every indexer
  key into the browser: the response body, the DOM, the browser cache, any
  saved HAR file, any screenshot.
- A holder of the CouchPotato API key reads all of them in one request.
- SEC-005 does not protect the Jackett key from that holder (SEC-005 gap (u)).

The fix cannot be masking alone. Measured at SEC-005 review round 1: with
today's `settings.save_group`, sending the displayed mask back overwrites the
stored key with the mask, an empty cell removes it, and a missing column is
refused. A masked read plus today's save would destroy stored keys on the
first unrelated edit. Masking and a save that can keep a stored credential
must ship together.

The cost of doing nothing: every load of the Settings page or the wizard keeps
copying every indexer key, and the Jackett key SEC-005 masks elsewhere, into
the response body, the browser cache and any HAR file or screenshot taken for
a bug report, so one shared capture discloses credentials that can only be
recovered by rotating the key at every indexer.

What this change does not make safe, stated here so nothing built from this
spec overclaims: a HAR file or saved page still contains the CouchPotato API
key, because it is in the URL of every API request the page makes, and that
key unlocks every indexer key to anyone who can reach the server. A capture
that includes a Show, the removal of a row holding a key, or an Undo or
put-back after that removal saved, contains that indexer key as well.

Threat model, one fact found at the review of this spec (measured
2026-11-23): the settings read was served as JSONP (`?callback_func=`) to a
page on any origin that knew the API key, so the whole read was readable
cross-origin, and after this change the token and every host would have
been. That is closed by a separate fix that ships ahead of this spec (D10,
see Dependencies). The rule it leaves for this design: the token must never
authorise anything on its own.

## Owner decision D1 (2026-11-23)

The full record of decisions D1 to D11 is under "Owner decisions" below.

"Dots with a Show button." A saved key is shown as dots on the Settings page;
a button fetches and shows the real key for that row.

Stated plainly, because it bounds what this spec can claim: with a Show
button, a holder of the CouchPotato API key can still read every indexer key,
one explicit request per key. This spec therefore does NOT stop that holder.
What it changes is that keys are no longer in the bulk settings read (and so
not in every page load, cache entry, HAR or screenshot), and that each reveal
is a separate, logged request. Decision D4 confirms the limit: the reveal route
is gated by the API key and the Origin check alone. Decision D2 adds one
reveal the user does not ask to see: removing a row that holds a stored key
fetches that key so Undo can restore it.

## Proposal

As amended on 2026-11-23 to agree with the acceptance criteria and the owner
decisions. Where this summary and a criterion differ, the criterion governs.

1. **Declare which columns are credentials.** The `combined` option gains a
   `secret` list beside `combine` and `pairing` (`newznab`: `api_key`;
   `torrentpotato`: `pass_key`), and an `address` list naming the column a
   secret is sent to (`host` in both), which decision D3's log line needs
   (AC-SEC-18). One Settings method derives each from the registered options,
   as `combine_groups()` does (AC-ARCH-1).
2. **Mask on read.** `getValues` returns, for a secret column, a comma-joined
   value with one fixed mask per non-empty stored cell of that column and an
   empty string per empty cell. The count is that column's own stored cell
   count, not the padded row count, and the mask does not reveal a key's
   length (AC-QA-1). Applies to every reader of `getValues` (the settings API,
   the Settings page, the wizard).
3. **A freshness token.** The read also returns, per combine group, inside
   `combine_state[section]`, a token that is a keyed hash of every stored
   column of the group. The key is random per process and held in memory only,
   so a restart makes earlier tokens stale (AC-SEC-3, AC-ARCH-5, AC-OPS-11).
4. **Keep-by-reference on save.** In `settings.save_group`, a secret cell is
   either a string (a new value, validated as today) or the object
   `{"keep": <row index at read time>}`. A save that contains any `keep` must
   carry the token from the read it was built on; the server refuses it, and
   writes nothing, when the stored group no longer matches the token or the
   index is out of range. This reverses SEC-004 owner decision D5 (no
   stale-save token) for saves that contain a `keep`, and only for those: a
   save of plain strings with no token behaves as on master (AC-SIMP-7). Any
   string containing the mask text is refused as a secret cell value, so a
   client that has not been updated cannot write dots over a key (AC-DATA-2).
   A `keep` is accepted on a row whose address changed, and logged (D3,
   AC-SEC-18). A save carrying any `keep` is refused when the request is
   demonstrably from another origin, an origin listed in `cors_origins`
   included (D9, AC-SEC-21).
5. **Reveal.** One new route returns one secret cell (`section`, `column`,
   `row`, `token`) by POST with a JSON body, gated by the API key and the
   Origin check alone, as the Jackett routes are (D4), and logged at INFO with
   section, column and row only, never the value. `row` is the secret column's
   own cell index, so a reveal is answered on a misaligned group too (D11).
6. **Settings page.** A secret cell is a password field whose value is never
   the mask: the saved state is carried by the placeholder (AC-DESIGN-1). Each
   stored cell has one Show/Hide button, a 44 px target, labelled by column and
   row number and never by the row's name or host (AC-A11Y-1). Untouched cells
   are sent as `keep`, edited cells as the typed value; a cell typed into and
   then emptied counts as untouched (D8). The Jackett sync keeps working: a
   merge sync builds its rows server-side and is unaffected by masking. The
   page has no reorder control: the only page actions that change a row's
   position are Undo's re-insertion and the put-back of D7, which appends.
   Remove fetches the row's stored key through the
   reveal route before the row is taken off screen and holds it in page memory
   for as long as Undo is offered, so Undo can restore the row after the
   removal has saved (D2, AC-DATA-8). If that restore is refused because the
   group changed elsewhere, the row can be put back after the reload, appended
   as a new last row with its key (D7, AC-DATA-21). On a misaligned group the
   page sends each stored key as shown or typed text and holds the save until
   it can (D11, AC-DATA-25).
7. **Wizard.** The wizard masks saved keys and keeps them with `keep`. It has
   no Show button and makes no reveal call (D5). Its Remove has no Undo
   (measured: `removeIndexer` in `wizard.html` splices the entry and nothing is
   written until Continue), so it needs no fetch either.

## Dependencies

- **The JSONP fix on the settings read (D10).** A separate small spec and PR,
  started by the orchestrator on 2026-11-23, refuses `callback_func` on the
  `settings` route. It must be on `master` before P1 of this spec merges,
  because P1 puts the freshness token into the settings read. This spec does
  not specify that fix. It only asserts its effect, in AC-SEC-1, so a
  regression of it fails here too.

## Not in scope

- Masking `core.api_key` (deliberately readable; see
  `test_settings_credential_masking.py`).
- Encrypting credentials at rest in `config.ini`.
- The outbound-proxy gap (SEC-005 gap (j); owner decision 2026-11-23: left
  documented).
- Storing each indexer as one record instead of parallel lists.
- Combined groups with no secret column. The three automation URL groups
  (`imdb`, `itunes` and `letterboxd`, columns `automation_urls_use` and
  `automation_urls`) and any other combined group that declares no `secret`
  column are untouched: their values are not masked, they have no Show
  button, no `keep` and no reveal, and their saves are accepted exactly as on
  master, with no token sent by the page and none required (AC-SIMP-7). The
  only thing they gain is an exemption entry in the sweep of AC-SEC-13.
- A Show button, a reveal call or Undo in the setup wizard (D5).
- A control to reorder rows. Neither page has one today and this change adds
  none; reorder by `keep` is a server capability, tested on the server.
- The JSONP fix itself, and JSONP on any route other than `settings` (D10).
- `keep` on a misaligned group (D11: it stays refused).
- A login-session requirement on the reveal route (D4).
- The freshness token on saves that carry no `keep` (vetoed at planning;
  SEC-004 gap 4 stays open for those).

## Open questions: answered by the planning cycle, and what is still open

Answered:

- Rollback (`config.ini` unchanged, nothing new persisted): answered by
  AC-SIMP-2 and AC-DATA-11, which includes a run of the previous release's
  Settings against a file the new code wrote.
- Third-party scripts: a script that reads indexer keys from the settings read
  breaks and must use the reveal route; one that calls `settings.save_group`
  with every column as a string keeps working. Answered by AC-SIMP-7 and
  AC-QA-8, and documented as a breaking change by AC-OPS-12.
- Whether any server-side reader consumes `getValues` output instead of the
  parser: answered by AC-DATA-12 (a static guard) and AC-ARCH-3. Measured on
  2026-11-23 by a search of `couchpotato/` (Python and templates): no caller of
  `getValues` or `view` outside `couchpotato/core/settings.py`.
- Automation and provider readers keep reading real keys: answered by
  AC-ARCH-3, AC-DATA-12 and AC-OPS-9.
- Whether the freshness token also closes SEC-004 gap 4 for saves without a
  `keep`: answered no. Vetoed at planning (see "Vetoed at planning"); AC-SIMP-7
  and AC-QA-8 pin the result.

Settled after the planning cycle:

- **A misaligned group that holds stored keys.** Settled by D11, before P2 is
  built: a reveal is answered on a misaligned group, addressed by the secret
  column's own cell index; `keep` stays refused there; the page sends each
  stored key as shown or typed text and holds the save until it can
  (AC-QA-13 as amended, AC-DATA-25, AC-A11Y-20). The wizard still writes
  nothing for a misaligned group and its pointer to Settings now leads to a
  repair that loses no key.

Still open (none blocks slicing; each names where it must be settled):

- **The `address` declaration (D3).** AC-SEC-18 needs to know which column a
  secret is sent to, and AC-ARCH-1 forbids naming a column in `settings.py`.
  This spec adds an `address` list to the combined option for it. That
  declaration was written after the planning cycle and was not examined by
  lens-architecture or lens-simplicity; the alternative (log on a change to
  any non-secret pairing column) was rejected here because `use` is a pairing
  column in both groups, so switching a row off would be logged as an address
  change. To be confirmed in the P1 slice review.
- **The existing removal tests.** AC-A11Y-4 requires the removal and Undo
  tests in `tests/e2e/settings-combined.a11y.spec.ts` to pass with their
  assertions unedited. Remove becomes asynchronous for a row with a stored key
  (D2). Whether those tests' fixtures hold stored keys, and whether their waits
  tolerate the extra request, was not measured for this amendment.
- **The put-back line has no way to dismiss it (D7).** AC-DATA-21 keeps the
  removed row and its key in page memory until put-back is pressed or the page
  is left, and nothing else withdraws the line. A user who does not want the
  row back has the line, and the key in memory, until they leave the page. A
  Dismiss control would end both and was not part of D7. To be settled in the
  P3 slice review; adding one is a small change to AC-A11Y-19 and AC-SEC-20.
- **A fetch open at `pagehide`.** How Chromium and WebKit treat a reveal that
  is open when the page enters the back/forward cache (aborted, delivered late
  or never settled) was not measured. AC-DATA-19 (vii) is written to be safe
  under all three.

### Security (lens-security)

- **AC-SEC-1:** With three Newznab rows holding distinct keys and two TorrentPotato rows (one holding a Jackett key after a sync), the raw body of `GET /api/<key>/settings` contains none of those key strings, in plain, JSON-escaped or URL-encoded form, and the Jackett key appears nowhere in it. Proof: integration, a real HTTP request and a search of the raw response bytes. The settings read is also requested as `GET /api/<key>/settings?callback_func=x` with a foreign Origin header: that request is refused (the D10 fix, whose status and body are that fix's to state), and the raw response, whatever its content type, contains none of those keys in plain or Python `repr`-escaped form, no host of any row and no freshness token. A regression of the D10 fix therefore fails this test. Proof adds: one more real request, with the fixture including a key whose `repr` form differs from its JSON form (a quote and a backslash). *(amended 2026-11-23, owner decision D10)*
- **AC-SEC-3:** The freshness token is keyed, and its key is random per process and held in memory only: two Settings instances holding byte-identical stored groups but different token keys produce different tokens, the token never equals an unkeyed hash (SHA-256, SHA-1 or MD5) of the stored columns joined in any order, and the token key appears in no API response and no log line. Proof: unit. The MAC input is an unambiguous encoding of the section name, each column name and each column's stored text (for example a JSON array of name and text pairs), not the texts joined: two groups whose stored columns are byte-identical produce different tokens, and two states that split the same text differently across columns produce different tokens. A submitted token is compared with `hmac.compare_digest`. Proof adds: unit for both collisions, and a code read for the comparison. *(amended 2026-11-23, lens-security review of the amendment)*
- **AC-SEC-4:** The reveal route returns a value only for a (section, column) pair where the column is in a registered combined option's declared `secret` list. Requests naming `core.password`, `core.api_key`, a core session secret option, `torrentpotato.jackett_api_key`, any non-combined `password` typed option, a non-secret column of a combine group (for example `newznab.host`), a column of the other group, a hidden or non-readable option, or an unregistered section each return a refusal carrying no stored value. Proof: integration, one real HTTP request per pair. (Merges part of AC-QA-10.)
- **AC-SEC-5:** The reveal route refuses, with no value in the body, a row given as JSON true, false, -1, "0", 1.5, null, a list, an object, or an integer equal to or beyond the named secret column's own stored cell count (D11: `row` is that column's cell index, which on an aligned group is the row index); JSON true does not return row 1 and -1 does not return the last row. Proof: integration. (Merges part of AC-QA-10.) *(amended 2026-11-23, orchestrator decision D11)*
- **AC-SEC-6:** The reveal route refuses, with no value in the body and no key in any log record: a request with no API key or a wrong one (401); a request whose Origin or Referer is another origin, or with neither header (403); a GET; a POST whose content type is not `application/json`; a POST carrying any query parameter other than `t`; a body with a missing or extra top-level key; a missing token; a token from before the group last changed. The gate is the API key and the Origin check and nothing else: the route does not look for a login session, so with a password set and no session cookie a request carrying the right key and a same-origin Origin header is answered (D4, AC-SEC-19). The route is listed in `ORIGIN_CHECKED_API_ROUTES` and has its own origin-check integration test in the shape of `tests/integration/test_jackett_routes_origin_check.py`. Proof: integration, one real request per case. (Merges part of AC-QA-10; the token requirement stands against the vetoed AC-SIMP-8, see below.) *(amended 2026-11-23, owner decision D4)*
- **AC-SEC-8:** After driving one successful reveal and one of each refusal in AC-SEC-4 to AC-SEC-6 with the server's real logging (PrivacyFilter attached, dev mode off), a search of the log file finds no stored secret value and no row host or name; a refusal naming an unregistered section or column logs a placeholder, not the caller's text, and a caller string containing a newline does not create a second log line. Proof: integration, reading the log file after the run.
- **AC-SEC-9:** A reveal handler that raises (forced in a test) returns the generic error body and writes a log entry containing no stored secret value. Proof: unit with a forced exception.
- **AC-SEC-11:** An accepted `keep` resolves only to the cell at that index in the same section and the same column at read time; no accepted save can place a stored secret value into a non-secret column or another section. Proof: a unit test drives `keep` in every position it can and then reads every non-secret column.
- **AC-SEC-12:** The per-column route `settings.save` with section `newznab` and name `api_key`, and with section `torrentpotato` and name `pass_key`, is refused and writes nothing, whatever the value, including the mask text. Proof: integration.
- **AC-SEC-13:** Every column of every registered `combined` option is either declared in its `secret` list or listed in a column-level exemption with a stated reason (the three `automation_urls` groups included). A sweep test over the raw declarations fails when a column listed in `secret` is missing from `combine`, and when a credential-shaped column (name containing key, pass, password, token or secret) is added to a combined option without a `secret` entry or an exemption. Proof: unit sweep, proven by adding a fake credential column and watching it fail. (Merges AC-OPS-10.) The sweep also fails when a group declares a `secret` column with a missing or empty `address` list, or an `address` column that is not in `combine`, or a `secret` column that is not in `pairing` (AC-DATA-25 relies on it), so the next credential group cannot ship with the record of a moved key silently absent or with a stored key outside the rows a page shows. Proven the same way, by removing `address` from a fixture declaration. *(amended 2026-11-23, lens-security review of the amendment)*
- **AC-SEC-14:** On the Settings page, after load and before any Show press, no element value, attribute or text node in the DOM contains a stored key; after Show then Hide, the key is again absent from the field's value; the revealed value is never written to localStorage, sessionStorage, a cookie or any URL, and the reveal request carries its parameters only in the JSON body. In the wizard, which has no Show (D5), no element value, attribute or text node contains a stored key at any point from load to the end of the step, and the wizard sends no request to the reveal route (AC-QA-25). A key fetched for Remove (D2) is held as AC-SEC-20 states. Proof: E2E inspecting `document.documentElement.outerHTML`, input values, storage and the request log. *(amended 2026-11-23, owner decision D2 and D5)* The Show then Hide scan is repeated after a re-read that replaces the rows, and at each scan the panel's `values` for the section holds no fixture key, so a copy that would only reach the DOM on a later re-derive is caught. *(amended 2026-11-23, lens-security review of the amendment)*
- **AC-SEC-16:** `docs/technical-debt.md` no longer lists "Credentials in combined rows are returned unmasked by the settings read" (SEC-005 gap u) as open: the entry is closed and states what this change closes (indexer keys absent from the bulk read, from every page load and from the browser cache, and from a capture of a page load in which nothing was shown, removed or restored) and what remains open, in these words or plainer: any holder of the CouchPotato API key can read every indexer key through the reveal route, one logged request per key, because the route is gated by the API key and the Origin check alone and needs no login session (D4); the Settings page itself makes a reveal request when a row holding a stored key is removed (D2), so a reveal line in the log means Show or Remove; and a save may keep a stored key on a row whose address was changed, which sends that key to the new address and is logged without the address (D3). The entry also says, in these words or plainer: a HAR file or saved page still contains the CouchPotato API key, which unlocks every indexer key to anyone who can reach the server, so after sharing one, rotate the API key; a capture that includes a Show, the removal of a row that holds a key, or an Undo or put-back after that removal saved, contains that indexer key; the Origin check stops pages on other origins in a browser, not scripts; and a save carrying a `keep` is refused from another origin, `cors_origins` included (D9). The entry does not claim that holder is stopped, and Jackett item 5's pointer to it is updated to match. Proof: reading the docs. (Merges AC-SIMP-13 and AC-PROD-10.) *(amended 2026-11-23, owner decision D2, D3 and D4)* *(amended 2026-11-23, lens-security review of the amendment and owner decision D9)*
- **AC-SEC-17:** Privacy: this change collects no new personal data; the only new persisted records are two INFO lines, the reveal line and the kept-on-a-changed-address line of AC-SEC-18 (each: section, column, row index), retained under the existing log rotation; no new third-party request is introduced, shown by a test or a search that the reveal and save paths make no outbound HTTP call. Proof: review of the diff plus a log read. *(amended 2026-11-23, owner decision D3)*
- **AC-SEC-18:** A `keep` is accepted on a row whose address, or any other column, changed between the read and the save (D3): the save is written and the stored key now sits beside the new address. For each kept cell whose row's address changed, the server logs exactly one INFO line saying that a stored secret was kept on a row whose address changed, naming the section, the secret column and the read-time row index and nothing else: no key, no old or new address, no row name. "Address" is the column or columns the combined option declares in an `address` list (`host` for both groups), read through one Settings method as `secret` is. The comparison is between the submitted cell and the stored cell at the keep index (not at the submitted position, so a reorder alone logs nothing), as exact text with no trimming, case folding or URL normalisation, so a change of case only, or of leading or trailing whitespace only, still logs: the line cannot be suppressed by dressing a new address up as the old one. A change to a non-address column only (`use`, `extra_score`, a name) logs nothing. The line is written only when the save is written, never for a refused save. Reasoning, recorded because it is why this is accepted and not refused, and corrected after the security review showed the first version was false for one actor. What stops an actor from using `keep` to move a key is, in order: the strict-JSON transport (a cross-site form or `text/plain` write to `settings.save_group` is refused 400, measured); the CORS allow-list (`cors_origins` is empty by default, so no other origin can send JSON); and the Origin refusal of AC-SEC-21 (D9), which refuses any `keep` from a demonstrably cross-origin request, an origin listed in `cors_origins` included, because that origin can read the settings reply, and so the token, but cannot use the reveal route. The token is a defence against one actor only: one that can send JSON but cannot read a reply (for example a blind server-side request forgery). The token never authorises anything on its own. Whoever passes all of these is the same-origin page or a script holding the API key, and that holder can read every key through the reveal route anyway (D4), so refusing a `keep` on a changed address would cost the operator a retyped key on every address correction and stop nobody. Limit, stated in the docs (AC-SEC-16, AC-OPS-12): this line, not a reveal line, is the only record that a key went to a new address. Proof: unit, AC-QA-24. *(added after the planning cycle, owner decision D3; not lens-reviewed at planning)* *(amended 2026-11-23, owner decision D9)*
- **AC-SEC-19:** The reveal route is gated by the API key and the Origin check alone (D4). With `core.password` set and auth required, a POST carrying the right API key and a same-origin Origin header and no session cookie returns the cell; the same request with a valid session cookie and a wrong API key is refused 401. The limit this leaves is recorded in three places in plain words (AC-SEC-16 for the debt entry, AC-OPS-12 for the API reference and the upgrade note): any holder of the CouchPotato API key can read every indexer key through the reveal route, one logged request per key. Proof: integration, two real requests against an app with a password set, plus a doc check. *(added after the planning cycle, owner decision D4; not lens-reviewed at planning)*
- **AC-SEC-20:** A key fetched for Remove (D2) lives in page memory only, and each held key is in at most one of three named fields of the Settings panel's group state at a time. Field 1, the held removal (the object `removeGroupRow` builds): from the fetch until Undo is pressed, when the key moves to field 2 if a save carrying the removal has been sent and is dropped otherwise (AC-DATA-18). Field 2, the restored-cell hold, keyed to the restored row object and not to a position: from Undo, or from a put-back, until a save of the group that includes that row is accepted. Field 3, the put-back hold of D7 (AC-DATA-21): the removed row's cells and its key, from a re-read that replaced the rows while field 2 was held, until put-back is pressed. A move between fields overwrites the source in the same step. None of the three is inside the row cells, none is read by any template binding, none is on the `combinedField` component, and none is copied into the panel's `values`. In all three the key is never written to the DOM (no element value, attribute, `data-` attribute, ARIA attribute or text node), never placed in an input's value (a restored or put-back row shows its secret cell in the saved rest state of AC-DESIGN-1, and its Show control is as AC-SEC-22 states), never written to localStorage, sessionStorage, IndexedDB, a cookie or a URL, never passed to `console`, a toast, an announcement region or an error message, and never sent anywhere except as that cell's string in a `settings.save_group` JSON body. Each field is dropped by overwriting it. Field 3 is dropped at the first of: put-back being pressed (the key moves to field 2 for the appended row); a later removal in the same group reaching field 3, since one put-back is held per group; `pagehide`. The Remove fetch is the one reveal route with the request shape of AC-QA-9 and nothing that marks its purpose, so it is gated and logged server-side exactly like a Show (AC-OPS-6); the page fetches only the removed row's own stored secret cells, never another row's. Twenty-eight criteria were folded into a neighbour that tests the same thing; each surviving line names what it absorbed. By lens, the folded numbers are: security 2, 7, 10, 15; QA 2, 5, 10, 16, 17, 19; simplicity 4, 11, 13; product 2, 3, 4, 7, 8, 10; design 8; accessibility 15; architecture 7, 12, 13; operability 2, 5, 7, 10.

Three overlaps were contradictions and were settled by the harness precedence order:

- Mask plus typed text: lens-qa left it open and allowed a new key made only of the mask's character at any other length; lens-data refuses any string containing the mask. Data loss outranks, so AC-DATA-2 stands and AC-QA-7 was narrowed to a shorter length.
- Mask positions on a misaligned group: lens-data said one position per stored row, lens-qa said one per stored cell of that column. The per-column rule stands (part d of AC-QA-1) because the wizard and the misaligned notice read each column's own count; a keep on a misaligned group is refused either way (AC-DATA-6).
- The token's key: every lens that addressed it converged on a random per-process key held in memory, which AC-SEC-3, AC-SIMP-2, AC-DATA-11 and AC-OPS-11 now state.

What the decisions leave true, stated once so no document built from this spec
overclaims:

- **D4 limit.** Any holder of the CouchPotato API key can read every indexer
  key through the reveal route, one logged request per key. A login password
  on the web interface does not change that, and the Origin check stops pages
  on other origins in a browser, not scripts. This change removes indexer keys
  from the bulk read, from every page load and from the browser cache. It does
  not make a capture safe: a HAR file or saved page still contains the API
  key, which unlocks every indexer key to anyone who can reach the server, so
  the remedy after sharing one is rotating the API key; and a capture that
  includes a Show, the removal of a row holding a key, or an Undo or put-back
  after that removal saved, contains that indexer key.
- **D2 not lens-reviewed.** The Remove fetch was proposed by the orchestrator
  after the planning cycle and no planning lens examined it. Its criteria are
  marked. It also means a reveal line in the log is not always a person
  choosing to look at a key: removing a row that holds one produces the same
  line, and the page then holds that key in memory for as long as the Undo
  line, or after D7 the put-back line, is shown, with no time limit.
- **D7 limits.** Put-back can create a duplicate row. Its line has no
  dismiss control (open question). It does not cover Undo followed by leaving
  the page before the restoring save is answered: a refusal of that leave
  flush is seen by nobody. The a11y criterion for the control (AC-A11Y-19)
  was not lens-reviewed.
- **D8 limit.** The pages never clear a stored key by emptying its cell. A
  script sending plain strings still can.
- **D9 limit.** The refusal applies to a request that is demonstrably from
  another origin. A script holding the API key sends no Origin header, or a
  matching one, and is not stopped; D4 already says that holder is not.
- **D3 limit.** A key kept on a row whose address was changed is sent to the
  new address at the next search. The only record is the INFO line of
  AC-SEC-18, which names no address.
- **D6 in the wizard.** The wizard already replaces its rows at once when the
  store changed and says afterwards that unsaved edits were discarded (SEC-004
  AC-DATA-23, kept by AC-SIMP-12 and AC-DATA-13). D6's "says so before
  discarding" is therefore met on the Settings page only; the wizard discards
  first and says so after. This is existing behaviour and is left as it is.

## Slices

A proposed build order of independently reviewable PRs. Each slice is built
through `/tdd-task`, reviewed on its own diff, and leaves `master` releasable,
because every commit on `master` publishes a beta.

**Hard constraints.**

1. Masking on read must never ship without the save that can keep a stored
   credential: the PR that turns masking on either contains that save or lands
   on a `master` that already has it.
2. No PR that makes the read mask a secret cell may land unless the Settings
   page and the wizard on that `master` have each passed the masked-read E2E of
   AC-QA-27. This follows from the code as it is today: both clients send back
   the cells they read (`groupPayloadRows`, `newznabRowForEntry`), so a masked
   read in front of an unchanged client makes every save of those two groups a
   refused save (no key is lost, AC-DATA-2, but the group cannot be edited).
   Masking is therefore the last behaviour switched on, in P5.
3. A slice that changes a security property updates every document asserting
   the old property in the same PR (AC-OPS-15 is the first use of this rule).
4. The D10 fix is on `master` before P1 merges (see Dependencies).
5. D11's reveal rule is built in P2 as written here. It is not left to P3.

If the slices are merged differently, P1 and P5 fold together and P3 and P4
must be in the same PR as them; the constraints do not move.
