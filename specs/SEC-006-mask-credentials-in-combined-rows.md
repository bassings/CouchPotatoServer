# SEC-006: credentials in combined rows are masked on the settings read

Status: planned, lean version adopted 2026-11-23 (D13); ready to build P1 once the forwarded-host fix is merged. This is one fresh rewrite, not an amendment: criteria are renumbered per lens and no old number is cited. The 144-criteria draft it replaces is preserved in the branch history (`spec/sec-006-mask-combined-credentials`). Follows SEC-004 (group save) and SEC-005 (Jackett key bound to its address).

## Problem

`GET /api/<key>/settings` (`Settings.view` / `getValues`) returns the combined options `newznab.api_key` and `torrentpotato.pass_key` in the clear. A combined control cannot be typed `password`, so the masking every other credential gets does not reach them (`tests/unit/test_settings_credential_masking.py` pins both as unmasked today). `newznab.api_key` holds every Newznab indexer key. `torrentpotato.pass_key` holds each row's pass key, which after a Jackett sync is the Jackett API key copied into every synced row, so the key `torrentpotato.jackett_api_key` masks is readable beside it (SEC-005 gap (u)).

Masking alone destroys keys. Measured at SEC-005 review round 1: with today's `settings.save_group`, sending the displayed mask back overwrites the stored key, an empty cell removes it, and a missing column is refused. Masking and a save that can keep a stored credential must ship together, and the pages must be able to save before the read is masked.

**What this change is worth, stated honestly.** SEC-006 stops indexer keys travelling in every load of the Settings page and the wizard, so they are no longer in the browser cache, in screenshots, or in a capture of a page load where nothing was shown or typed. A page on another origin, in a browser, cannot read a key through the reveal route, or keep, restore or move one. It does not protect the keys from anyone who holds the CouchPotato API key and can reach the server: they can read every key, one logged request at a time. The API key is in every page and every API URL, so any capture yields it, and so does any origin listed in `cors_origins`. A key that is removed or replaced stays in the server's memory until CouchPotato restarts or sixteen later removals or replacements in the same section push it out, and until then anyone with the API key and the token of the settings as they stood before can bring it back.

**The cost of doing nothing.** Every load of the Settings page or the wizard keeps copying every indexer key, and the Jackett key SEC-005 masks elsewhere, into the response body, the browser cache and any HAR file or screenshot taken for a bug report. One shared capture discloses credentials that can only be recovered by rotating the key at every indexer.

## Design

**1. Declarations.** The `combined` option gains a `secret` list (`newznab`: `api_key`; `torrentpotato`: `pass_key`) and an `address` list naming the column a secret is sent to (`host` in both), beside `combine` and `pairing`. One Settings method derives each, as `combine_groups()` does. A sweep fails when a `secret` column lacks a valid `address`, is not in `combine`, or is not in `pairing`.

**2. Masked read and token.** `getValues` returns, for a secret column, one fixed mask per non-empty stored cell and an empty string per empty cell, counted by that column's own stored cells. The mask equals its own trim, has no whitespace or comma, is at least eight characters and contains a non-ASCII character, so no real key contains it and no client normalisation changes it; any string containing it is refused as a secret cell value. The read also returns a per-group token in `combine_state[section]`: a MAC, under a random per-process key held in memory only, over an unambiguous encoding of the section name, every column name and every column's stored text. A submitted token is compared with `hmac.compare_digest`. A key already stored with the mask text in it cannot be saved with its group, or merged by a Jackett sync, until it is corrected in `config.ini` (a recorded limit; nothing on master writes the mask). The token never authorises anything without the API key. On a save it proves the caller built on the current state; in a `restore` reference it selects an entry in the hold, so it is treated like the API key and kept out of logs.

**3. Secret cells on save.** In `settings.save_group` a secret cell takes one of three forms.

| Form | Meaning | Refused when |
|---|---|---|
| a string | A new value, validated as today. | It contains the mask text, or fails today's cell checks. |
| `{"keep": i}` | Store what cell `i` of this secret column holds now. | `i` is not a JSON integer in range (a bool, a float, a string, a negative number, null), the object has other keys, two cells name the same `i`, the token is missing or stale, the column is not secret, or the request is cross-origin (D9). |
| `{"restore": {"token": T, "row": i}}` | Store the text held when a save carrying token `T` left cell `i` unkept. | No such entry is held for this section and column (`restore_unknown`, checked first), any shape fault as for `keep`, two cells carry the same reference, the save's own token is missing or stale, or the request is cross-origin (D9). |

`i` always means cell `i` of the secret column, on aligned and misaligned groups alike. That is how reveal addresses a cell (D11) and how the providers already pair one: `getHosts` in `newznab.py` and `torrentpotato.py` sends key cell `n` to host cell `n`. Keep-by-cell-index therefore persists exactly the pairing searches already use, moves no key to a new host, and makes the first ordinary save of a misaligned group its repair. The server and the page have no misaligned case beyond the notice that exists today. A save's token is required when any cell is a `keep` or `restore` and checked whenever one is supplied. A token-less all-string save behaves as on master.

**4. The hold.** When a row save that carried a token is accepted, each non-empty stored secret cell that no `keep` in it names is held under `(section, column, token the save carried, i)`: its text exactly as `_stored_text` yields it, and nothing else. The rule reads `keep` indexes only and never compares hosts or names. The hold is process memory only, first-in-first-out with one bound (a module-level constant, 16 entries per section), and gone on restart. There is no age limit, no overall bound and no timer. Entries are made and consumed only after `_write_group` returns, under `_PASSWORD_SAVE_LOCK`; no hold operation raises an exception whose message contains held text or a token; held text reaches no response, log, file or backup. A `restore` substitutes the held text, is validated and written like any save, and consumes its entry after the write. An unknown reference is refused as `restore_unknown` before the token is checked, so a restore that landed with its reply lost is not mistaken for a stale save. A stale refusal lists the cells held under the token it carried, as column names and indexes only.

Stated limits. A removed or replaced key is not gone until CouchPotato restarts or sixteen later entries in that section push it out: a key replaced by typing is held as a removed one is, because the server cannot tell the two apart without comparing rows by content, which mispairs two accounts at one indexer. Until then, anyone with the API key and the group's token from just before the removal (from a settings read, a save reply or a capture taken at that moment) can restore the key beside any address and then reveal it. Restarting CouchPotato or rotating the API key ends this. Token-less all-string saves (scripts, pages loaded before the upgrade) and builder saves (the Jackett sync) hold nothing, so a row they drop is gone as on master. The wizard's removals are held and the wizard offers no restore.

**5. Reveal.** One new route, working name `settings.reveal_cell`: a POST of exactly `section`, `column`, `row`, `token` as strict JSON, listed in `ORIGIN_CHECKED_API_ROUTES`, gated as D4 says. It returns the one stored cell and logs one INFO line (section, column, row; never a value). An out-of-range row, a wrong type, a column not declared `secret` and a stale token are each refused without a value. It ships in the same PR as items 1 to 4.

| Where | Field | Content |
|---|---|---|
| settings read | `combine_state[section].token` | The group's token. |
| accepted save that carried a token | `token` | The fresh token, computed in the same lock hold as the write. The reply gains nothing else; a token-less save's reply is master's. |
| stale refusal | `held` | `[{"column": c, "row": i}, ...]` for entries held under the token the refused save carried; empty when none. On no other refusal. |
| reveal reply | `value` | The one stored cell. |

**6. Settings page.** A secret cell is a password input that never holds the mask: its rest state is a placeholder saying a key is saved, or "Not set". Each stored cell has a Show/Hide button labelled by column and row number, a 44 px target, in both themes and at phone width; a Show response is bound to the row object it was pressed on, never to a position. Each group holds the token issued with its rows, and a re-read that does not replace a group's rows leaves its token and origin indexes unchanged. One pure function builds every payload (debounced save, forced flush, leave flush) and never stringifies a non-string cell. Precedence for a secret cell: (1) a non-empty typed value; else (2) the row's `restore` reference; else (3) `keep` of a valid origin index; else (4) an empty string, only on a cell with no stored key; else (5) the payload cannot be built and nothing is sent. An emptied stored cell is not a typed value (D8). When a save is accepted, the page re-bases the origin index of every row object that save carried, wherever that object now is (on screen, the live removal, a row returned by Undo), to its position in the sent payload; gives every keyed row that save omitted the reference `(token the save carried, its index in that state)`; and adopts the reply's token, all before any later payload is built. Master copies a removed row's cells (`takeRow`), so the build must make the removal part of that walk.

**7. Undo.** One Undo per group, as on master, held in a single field. What Undo sends depends on what became of the save that carried the removal:

- Not sent yet: client-side, as on master; the row is a `keep` again.
- Accepted: `restore` with the token that save carried and the row's index in that state. The page knows both without any reply field.
- Refused: nothing landed, so `keep` of the origin index.
- Unanswered (open, or failed on the network): `keep` under the group's unchanged token, because a `restore` would be refused as unknown if the removal never landed. If it never landed the save is accepted; if it landed the token is stale and the refusal's `held` says whether the cell is held.

After a stale refusal and Reload the group shows at most one appended restorable line, withdrawn by the next edit, removal or added row exactly as master's Undo is. A removed row is offered there only when a save carrying its removal was accepted, or went unanswered and the refusal listed its index; a removal answered by a refusal is never offered. For the unanswered case the line says, by row number, that the row may already be in the list and to check before pressing Undo, because the refusal cannot tell a removal from a key another client replaced. When a save carrying a removal went unanswered and a later refusal, stale or `restore_unknown`, lists nothing for that row, the message says the row may already have been removed and that, if it is missing after reloading, its key must be entered again; it never claims the row was not removed. A listed index for a row that was only re-keyed and is still on screen is ignored. A button-action lock withdraws Undo, as on master. Apart from the user's own actions, no Undo control disappears: when the server no longer holds the row, the page says so when Undo is pressed.

**8. Wizard (D5).** The Newznab step shows saved keys in the rest state, sends `keep` for untouched and emptied cells (rows it does not show included) with the token of its read, and uses the server's stale refusal as its one changed-since-opened path. No Show, no restore, zero reveal requests.

**9. Logging and docs.** Exactly three new INFO lines: reveal; a key kept on a changed address (D3); a restore. Refusals keep the existing WARNING shape without values. Nothing is logged for holding or eviction. Each user-facing limit is written in full once, in `docs/technical-debt.md`; `docs/reference/API.md`, `UPGRADING.md` and `CHANGELOG.md` link to it.

## Not in scope

- Masking `core.api_key`, encrypting `config.ini`, the outbound-proxy gap (SEC-005 gap (j)), and storing each indexer as one record.
- Combined groups with no `secret` column (the three automation URL groups): unmasked, no token sent or required, saved exactly as on master.
- A Show button, Undo or restore in the wizard (D5); a control to reorder rows; a login-session requirement on reveal (D4).
- The token on saves that carry none (SEC-004 gap 4 stays open for those).
- A route to list, read or delete held entries; an age limit on them; restoring across a restart; more than one Undo per group; an Undo for a key replaced by typing.
- Undo surviving a button-action lock (master's behaviour is kept).
- The D14 fix (credentialled CORS limited to `/api/`), the two prerequisite fixes themselves, and JSONP on any other route.

## Prerequisites

Both must be on `master` before P1 merges. This spec builds neither and asserts the effect of each once (AC-SEC-2), so a regression of either fails here.

- **JSONP refused on the settings read (D10).** Merged as #630 (`dd80c7574`), verified an ancestor of `master`.
- **`X-Forwarded-Host` cannot vouch for an origin on the CORS allow-list.** `specs/FIX-2026-11-23-origin-check-allow-listed-forwarded-host.md`, commit `a75b8af15` on `fix/origin-check-allow-listed-xfh`, in review; measured 2026-11-23 as not an ancestor of `master`. Without it D9 and the reveal gate do not hold against a listed origin, and P1's doc text would be false in a published beta.

## Acceptance criteria

Each criterion ends with the slice or slices that build it. "Unit" and "integration" are pytest; integration means a real HTTP request through the real route. UI criteria are proven by E2E in both themes at phone width (375 px) and desktop unless stated. Every E2E arms its observers before the action, waits on a response or an advanced clock and never a fixed sleep, and first proves its probe is hostile.

### Security (lens-security)

- **AC-SEC-1:** With three Newznab rows holding distinct keys and two TorrentPotato rows (one a Jackett key after a sync), the raw body of the settings read contains none of those keys in plain, JSON-escaped or URL-encoded form. Proof: integration, a search of the raw response bytes; fails if masking is skipped for either column. [P3]
- **AC-SEC-2:** Prerequisite regressions, one each. (a) The settings read requested with `?callback_func=x` and a foreign Origin is refused and its body contains no token and no host. (b) With `cors_origins` listing `http://dash.example`, a `keep` save and a reveal sent from that Origin with `X-Forwarded-Host: dash.example` are each refused 403; the test first asserts the CORS preflight for that header set succeeds, so the probe is hostile. Proof: integration. [P1]
- **AC-SEC-3:** The token is keyed and its key is random per process and in memory only: two Settings instances with byte-identical groups produce different tokens; the token equals no unkeyed hash of the stored columns; the MAC input is an unambiguous encoding, so two sections with identical columns, and two states that split the same text differently across columns, produce different tokens; the key appears in no response and no log; comparison uses `hmac.compare_digest`. Proof: unit plus code read. [P1]

  *Note, 2026-11-23.* The token is computed with `hmac.digest`, so the session-MAC guard in `tests/unit/test_session_secret_store.py` now matches every standard-library MAC call (`hmac.new(`, `hmac.digest(`, `hmac.HMAC(`) and allows exactly two files (`couchpotato/__init__.py`, `couchpotato/core/settings.py`), and asserts the session-signing symbols appear only in `couchpotato/__init__.py`.
- **AC-SEC-4:** Reveal returns a value only for a column in a registered `secret` list. `core.password`, `core.api_key`, `torrentpotato.jackett_api_key`, any `password`-typed option, a non-secret column of a group, a column of the other group, a hidden option and an unregistered section are each refused with no stored value in the body. Proof: integration, one request per pair. [P1]
- **AC-SEC-5:** Reveal refuses, with no value: a row given as true, false, -1, "0", 1.5, null, a list or an object, or an integer at or beyond the secret column's own cell count (true does not return row 1; -1 does not return the last row); a missing token; a stale token. It never answers with whatever cell now sits at that index. Proof: integration. [P1]
- **AC-SEC-6:** The reveal gate is the API key and the Origin check and nothing else (D4). Refused with no value: no or wrong API key (401); a foreign Origin or Referer, or neither header (403); a GET; a content type other than `application/json`; a query parameter other than `t`; a missing or extra top-level key. With `core.password` set and no session cookie, the right key and a same-origin Origin are answered; a valid session with a wrong key is refused. The route is in `ORIGIN_CHECKED_API_ROUTES` with its own test in the shape of `tests/integration/test_jackett_routes_origin_check.py`. Proof: integration. [P1]
- **AC-SEC-7:** D9. A `settings.save_group` request with any non-string cell is refused 403, nothing written and the hold unchanged, when `_cross_origin_post(request)` is true. The check is in the API dispatch, reads the object the strict-JSON parse produced (no second parser, no scan of body text) and counts any member of any row that is not a JSON string. Cases, one request each: a `keep` from a listed origin is refused; the same body from the server's own origin is accepted; an all-string save from the listed origin is written as on master; a `keep` with neither Origin nor Referer (a script) is not refused by this rule; `{"keep": true}` from the listed origin is refused here, not passed on; a `restore` from the listed origin is refused and its entry is still restorable afterwards from the server's own origin. One WARNING names the route and reason, with no cell value and no token. Proof: integration. [P1]
- **AC-SEC-8:** No accepted save can place a stored or held secret into a non-secret column, another secret column or another section, and the per-column `settings.save` of a secret column is still refused whatever the value. Proof: unit driving `keep` and `restore` in every position and then reading every other column and the other group; integration for the per-column refusal. [P1]
- **AC-SEC-9:** The hold leaks nothing. With a fixture key held, it appears in no settings read, save reply, refusal, reveal reply or error body, in no log record at DEBUG with real logging and `PrivacyFilter` attached, and in no file under the data directory; the reveal route does not read the hold. An exception forced in each hold operation (add, take, list by token, evict), driven through the real `callApiHandler`, leaves a log and a response with no held text and no token, and leaves the parser and `config.ini` agreeing on the state the reply reports: a failure reply only with both holding the pre-save group and no entry from that save left; otherwise the accepted reply with its token. Proof: unit and integration. [P1]
- **AC-SEC-10:** The declaration sweep. Every column of every registered `combined` option is in its `secret` list or in a column-level exemption with a stated reason. The sweep fails for a `secret` column missing from `combine` or `pairing`, a `secret` column with a missing, empty or unknown `address`, and a credential-shaped column (name containing key, pass, token or secret) with neither a `secret` entry nor an exemption. Proof: unit sweep, proven by adding a fake credential column and by removing `address` from a fixture. [P1]
- **AC-SEC-11:** No SEC-006 server path logs a secret. Across a read, every save outcome, every refusal, a reveal and every reveal refusal, a hold, an eviction and a restore, no log record at DEBUG contains a fixture key, a row host or name, a token, or the token key. A refusal naming an unregistered section or column logs a placeholder, a caller string with a newline creates no second line, and a reveal handler that raises returns the generic error body. Proof: integration reading the log file. [P1]
- **AC-SEC-12:** The Settings page holds no stored key. After load and across Remove, Undo in each state of Design 7, a stale refusal, Reload and a restore, no fixture key is in the DOM (values, attributes, text nodes), the panel's `values` or group state, storage, cookies, the URL or console output, and the page sends zero reveal requests. After Show then Hide the key is gone from the input and the DOM; reveal parameters travel only in the JSON body. Proof: E2E with a reveal-request observer first proven by one Show; run in P2 against the rewritten read of AC-QA-10 and in P3 against the real masked read. [P2, P3]
- **AC-SEC-13:** Privacy. No new personal data is collected; the only new persisted records are the three log lines of AC-OPS-2 under the existing log rotation; a removed or replaced key (a credential, not personal data) is retained in memory only, as Design 4 states; the reveal and save paths make no outbound request. Proof: diff review plus a log read. [P1]

- **AC-QA-1:** Masking. Fixture: `newznab.api_key` = `K,,A_KEY_OF_EXACTLY_FORTY_CHARACTERS_LONG_X,k2 ,,` and three `pass_key` cells of lengths 1, 32 and 200 plus one legacy `b'...'` value. ### Data (lens-data)

- **AC-DATA-1:** Cell forms. A secret cell is a string, exactly `{"keep": <int>}` or exactly `{"restore": {"token": <str>, "row": <int>}}`. Each shape the table in Design 3 refuses (the mask or any string containing it; a bool, float, string, null or negative index; an index at or beyond the column's cell count; an empty object or extra keys; both forms in one object; a duplicate `keep` index or `restore` reference; either form in a non-secret column; either form with no token, another group's token or a stale one) refuses the whole save with `config.ini` bytes and mtime, the parser and the hold unchanged, and no stored value in the body or the WARNING. Proof: unit, one test per shape. [P1]
- **AC-DATA-2:** A kept key follows its cell index, never its position, on every group. Rows A (hostA, keyA) and B (hostB, keyB): saving B with `keep 1` then A with `keep 0` stores hostB,hostA and keyB,keyA; saving only B with `keep 1` stores hostB and keyB. On a group with three `host` cells and two `api_key` cells, a save sending `keep 0`, `keep 1` and an empty string for the third row is accepted, leaves both keys in their original cells, and `getHosts` returns the same host-to-key pairs before and after. Proof: unit. [P1]
- **AC-DATA-3:** What is held. Four rows with distinct keys, one with a leading space, one empty. A token-carrying save that omits row 1 makes exactly one entry, with the text byte for byte; omitting the row with the empty key makes none; replacing row 1's key with a typed string holds the old key; with two rows whose non-secret cells are identical and whose keys differ, removing either holds that row's key. No entry is made by a refused save, a save whose write to disk fails (forced), a token-less save or a builder save, and entries made earlier survive each. With 16 entries in a section a seventeenth evicts the oldest of that section only, no save is refused for the bound, and the other section is untouched. Proof: unit. [P1]
- **AC-DATA-4:** What a `restore` does. A `restore` placed in a row at any position stores the held text byte for byte beside whatever cells that row carries; the entry is then gone and the same reference is refused as `restore_unknown`, with the new token or the old. A save refused for any reason, or whose write fails, leaves every entry it named restorable. Two entries restored in the opposite order to their removal, and both in one save, each store their own key. Two saves restoring one reference released together from two threads: exactly one is accepted and the key is stored once, on each of 20 repetitions. A reference that was never issued, was already consumed, was evicted, or differs in section, column, token or row in any one respect gives the one reason `restore_unknown`, so a caller cannot learn which. Proof: unit. [P1]
- **AC-DATA-5:** A stale refusal lists, in `held`, exactly the entries of that section recorded under the token the refused save carried, as column and index only, and nothing for any other token or section; no other refusal carries the field. A save whose `restore` reference is unknown is refused as `restore_unknown` even when its token is also stale. Proof: unit. [P1]
- **AC-DATA-6:** Payload precedence is one pure function with the five results of Design 6, used by the debounced save, the forced flush and the leave flush. A stored cell typed into and then emptied (with or without whitespace) gives `keep` (D8); the same on a row carrying a `restore` reference gives the `restore`; an added row left empty gives an empty string; an unrecognised state gives "cannot be built" and never an empty string. The builder never stringifies a non-string cell: no payload cell equals `String({})`, `acceptGroup` no longer writes the sent payload into `values`, and `config.ini` never contains `[object Object]` after any save in the E2E suite. Proof: UI unit over the table of states, plus E2E for the typed-then-emptied cell asserting the body and `config.ini`. [P2]
- **AC-DATA-7:** Each group uses its own token. A re-read that does not replace a group's rows (another section's button action, `init()` run again over unsaved rows) leaves that group's token and origin indexes unchanged, and nothing a save or a reveal uses is read from `combineState` after the rows were derived. After a Jackett sync replaces the TorrentPotato rows, an edit to a synced row saves without a stale refusal. Proof: UI unit; E2E in which Newznab rows A, B, C have an unsaved edit, a second client removes A and adds D, a Jackett sync re-reads every section, and the Newznab save then sent is refused as stale with `config.ini` unchanged. [P2]
- **AC-DATA-8:** Re-basing covers every carried row object (data finding N1). Rows A0 B1 C2 D3. Remove A; its save S1 is held open. Type a new key into C. Remove B. Release S1 as accepted; the queued save S2 is built at once and accepted. Press Undo. The restoring save carries, for B, the reference (the token S2 carried, row 0), and `config.ini` then holds B's own key beside B's host and C's old key nowhere. Proof: UI unit, then E2E against the real server. [P2]
- **AC-DATA-9:** Undo sends what Design 7 states for each outcome of the removal's save. Not sent: no request of any kind, and the keys are unchanged. Accepted: the body carries the `restore` reference for that cell, `keep` for every other stored cell and the group's token; `config.ini` then holds every key beside its original host, the restored row at its own index with surrounding whitespace preserved. Refused: `keep`, and no key changes. Still open when Undo is pressed and then accepted: the queued save carries the `restore`. Still open and then refused: `keep`. A row with an empty key, an added row and a row with a typed, unsaved key each return exactly what the page had, with no `restore`. Removing D, then B, then A offers Undo for the last only and leaves `config.ini` holding the remaining row with its own key. Proof: E2E, with UI unit where the browser cannot be driven to the state. [P2]
- **AC-DATA-10:** After a stale refusal and Reload, at most one restorable line (data finding N2, option A). (a) Removal accepted, a second client then saves, Undo's save is refused as stale: the entry is still held; Reload shows the line; its Undo appends the row with its removal-time non-secret cells and the `restore`, and `config.ini` holds every key once beside its own host. (b) Removal landed and its reply was aborted in the browser: Undo sends `keep`, the refusal lists the index, Reload shows the line with the "may already be in the list" text, and Undo restores the key. (c) Removal answered by a stale refusal: Reload shows the row, no line and no Undo. (d) Two tabs: tab 2 replaces B's key; tab 1 removes B and its save is refused as stale with B's index listed: tab 1 draws no line. Proof: E2E. [P2]
- **AC-DATA-11:** The page tells the truth about an unanswered removal (N3). Remove B; the removal's response is aborted after the server wrote; the server's Settings is replaced by a fresh instance; Undo. The refusal lists nothing, and the message says row 2 may already have been removed and that, if it is missing after reloading, its key must be entered again. It never says the row was not removed. Proof: E2E. [P2]
- **AC-DATA-12:** A listed index for a row still on screen is ignored (N4). Type a new key into B; the save lands and its response is aborted. Edit A's host: the save is refused as stale and lists B's index. No restorable line is drawn, B's cell does not become a `restore`, and after Reload and one edit `config.ini` holds B's new key exactly once. Proof: UI unit plus E2E. [P2]
- **AC-DATA-13:** `restore_unknown` on the page. With the server's Settings replaced by a fresh instance between an accepted removal and Undo, nothing is written, the row stays on screen as an unsaved row whose cell is "Not set", and that reference is sent in no later request. Where an earlier save carrying the same `restore` went unanswered (its response aborted after the write, then a retry), the text says instead that the row may already have been restored and offers Reload (L1). Where that unanswered save also carried a removal (Undo of one row and Remove of another inside one debounce), the message also carries AC-DATA-11's text for the removed row, because a `restore_unknown` refusal lists nothing. Proof: E2E for all three. [P2]
- **AC-DATA-14:** Leaving and racing. `flushGroupsOnLeave` sends each waiting group's payload with `keepalive`, built by the same function with that group's own token, so a waiting `restore` leaves as a `restore`. When two saves built on one token race (the leave flush against an open save, or the `SAVE_WAIT_DEADLINE_MS` send-anyway path), the second is refused with nothing written and no key is deleted, duplicated or moved, under both orderings. Shown again from the back/forward cache after a flushed removal, Undo ends through path (b) of AC-DATA-10 with the key in `config.ini`. Proof: integration for both orderings; UI unit and E2E for the flush. [P2]
- **AC-DATA-15:** The wizard detects a key-only change by the token. Between its read and its save one stored `api_key` is replaced by another of the same length; the wizard's save is refused with nothing written, its changed-since-opened message is shown and the fresh rows replace those on screen. A stored key cell typed into and then emptied is sent as `keep` (D8). Proof: E2E. [P3]

### Design (lens-design)

- **AC-DESIGN-1:** Rest state. A secret cell on the Settings page follows the existing password field pattern in `field_types.html`: an `input type=password` whose DOM value is the empty string, with the pattern's saved-state placeholder when the read marks the cell non-empty and "Not set" when empty. Focus a stored cell, type `abc`, blur: the value is exactly `abc` and the save body carries `abc`. No `input type=text` is bound to a secret column's read value. Proof: E2E plus UI unit. [P2]
- **AC-DESIGN-2:** Each stored secret cell has exactly one Show/Hide control and no other new control. It reuses the text-button style of the combined control's Undo button, with visible text "Show" and "Hide", a bounding box of at least 44 by 44 CSS px on the Newznab and TorrentPotato cards, and no new component, icon or token; the design-system conformance check passes. Proof: E2E using `boundingBox`, plus `make verify`. [P2]
- **AC-DESIGN-3:** Show has four testable states: in flight ("Showing…", a second press sends nothing); shown (`type=text` holding the key, control reads "Hide"); hidden again (rest state, key out of the DOM); failed (rest state, with a message in the row's error box, `data-testid=combine-row-error`). A response is applied to the row object Show was pressed on: if that row was removed, or the rows were replaced or locked, before it arrives, it is rendered nowhere and held nowhere. Proof: E2E with the route stubbed to succeed, delay and fail. [P2]
- **AC-DESIGN-4:** Show never asks for a cell the server cannot name. On a cell with typed text it only toggles the visibility of that text (type `newkey`, press Show: zero reveal requests, the input shows `newkey`). No Show is drawn on an empty cell with no stored key, on an added row, or on a row carrying a `restore` reference until its save is accepted. A stored cell typed into and then emptied is a stored cell again and its Show is an ordinary reveal. Proof: E2E counting requests. [P2]
- **AC-DESIGN-5:** A revealed key does not outlive its context: every revealed cell returns to the rest state, key out of the DOM, when the group saves, when its rows are re-read (a Jackett sync included), on a tab change and when the rows lock. No timer re-masks: a revealed key is still shown 30 s later. Proof: E2E. [P2]
- **AC-DESIGN-6:** A stale refusal is shown in the combined control's save-error box (`data-testid=combine-save-error`), never only in the log, with one Reload action. Before Reload is pressed the text says that Reload discards what was typed and not saved, keys included (D6); typed values stay on screen until then; Reload replaces the rows and re-applies nothing. Where a removed row will be offered (AC-DATA-10) the text says row N can be restored after reloading; for AC-DATA-11 it carries that text; otherwise it says nothing about restoring. Proof: E2E with two loads of the page, a typed key present before Reload and absent after. [P2]
- **AC-DESIGN-7:** The restorable line sits after the last row and before Add, in the style of the existing removed line (`data-testid=combine-removed-line`). It says row N was removed and that Undo adds it back as the last row with its saved key; the unanswered variant adds that the row may already be in the list and to check first. Pressing Undo appends the row; the page never matches a removed row to a re-read row by host and never writes into another row. An edit, a removal or an added row withdraws it, as master's Undo. Proof: E2E plus UI unit that the appended row is last and no other row changed. [P2]
- **AC-DESIGN-8:** Copy names rows by number only. Every new message and name (reveal failed, stale save, restorable line, restore refused, may already be restored or removed) says "row N" in the wording the surface already uses, contains no host, name or key, and never the words "token", "stale", "index" or "reference". Proof: UI unit on the message builders plus E2E text assertions. [P2]
- **AC-DESIGN-9:** The wizard's Newznab step shows a stored key in the rest state of AC-DESIGN-1: the input value is empty, the placeholder carries the state, and neither the mask nor the stored key is bound through `x-model` (`newznabInitialEntries` no longer copies `row.api_key`). An untouched entry is known by its state, not by comparing strings. Proof: E2E with a seeded indexer plus UI unit on the wizard helpers. [P3]

### Architecture (lens-architecture)

- **AC-ARCH-1:** Which columns are credentials, and which column is their address, is declared only on the `combined` option and read through one Settings method each, derived as `combine_groups()` is. No literal `api_key`, `pass_key`, `host`, `newznab` or `torrentpotato` is added to `couchpotato/core/settings.py`, `couchpotato/__init__.py` or the Settings-page script. A synthetic combined option with a `secret` and an `address` column is masked, kept, held, restored and revealed with no other code change. Proof: search of added lines plus unit. [P1]
- **AC-ARCH-2:** Masking lives only in the bulk read path. After `view()` has returned masks, `get()`, `group_cells()`, `group_stored_rows()`, the Jackett sync builder and both providers' `getHosts` return the real keys, and an outbound search URL contains the real key and no mask. A static test asserts no module outside `settings.py` and the API layer calls `getValues` or `view`. Proof: unit, integration and a static guard. [P3]
- **AC-ARCH-3:** Placement. Token check, `keep` and `restore` resolution, the mask refusal and the hold are inside `Settings._save_group`, after a builder's rows are produced and before `_group_problems` runs; none is in `save_group_view`, a provider or the dispatch. The one check outside is D9, in the API dispatch, which decides nothing else. All of it, and the computing of the reply's token, happens under one hold of `_PASSWORD_SAVE_LOCK`; two consecutive `keep` saves from one client with no re-read between them both succeed. One function computes the token, `view`, `_save_group` and reveal all call it, and it reaches the client inside `combine_state[section]`, not as a new top-level key. The reveal route is registered by Settings beside `settings.save_group` and reads the cell through `group_cells`. Proof: code read plus unit. [P1]
- **AC-ARCH-4:** `STRICT_JSON_API_ROUTES` entries can state an optional key and a route with no rows array; no route-name special case is added to `_strict_json_body_ok` or `_strict_json_refusal`, and the refusal's log line no longer says "settings group save" for a route that is not one. Proof: code read plus unit. [P1]
- **AC-ARCH-5:** The hold is one small object owned by `Settings`, created in its constructor: an insertion-ordered mapping with add, take, list-by-token and evict and nothing else. No new module, thread or timer; lookups use `get` and `pop(key, None)`; it ends with the instance, as the token key does. Proof: code read. [P1]
- **AC-ARCH-6:** One client function decides what a secret cell is sent as (AC-DATA-6); it lives in `couchpotato/static/scripts/ui/`, is unit-tested beside `settings-values.js`, and both the Settings page and the wizard call it. It never compares a cell's text with a mask and no client file contains the mask literal. The Settings page has one function that calls the reveal route and only Show uses it; a `restore` reference lives on its row in the panel's group state, never in a row's `cells` or in `values`. Proof: code read plus UI unit. [P2, P3]

## Open items

Only what is unmeasured. None blocks P1.

- **A fetch open at `pagehide`.** Whether a browser aborts a non-keepalive save that is in flight when the page goes is not measured. A `restore` already in flight is not re-sent by the leave flush (master sends only what is waiting or queued), so it may be cut off; the row then stays removed and its key stays held until restart or eviction. Master behaves the same for any in-flight save. To be measured in P2 and recorded in the debt entry either way.
- **The leave-flush limit.** A refusal of the leave flush is seen by nobody. Undo, then leaving before the restoring save is answered, can leave the row removed with no page knowing. Recorded as a limit (AC-OPS-5); how often it occurs is unmeasured.
- **Existing removal tests.** Whether the removal and Undo tests in `tests/e2e/settings-combined.a11y.spec.ts` pass with their assertions unedited once the row carries a Show button is not measured; AC-A11Y-3 requires any edit to be listed with its reason.
- **Master's row copy.** `takeRow` copies a removed row's cells and `acceptGroup` walks only what was sent. How the build gives the removal an identity the re-base can reach (AC-DATA-8) is left to P2; the criterion fixes the behaviour, not the mechanism.
- **Browser side of D9.** The server side of the Origin refusals is measured; that a browser always sends `Origin` on a cross-origin POST rests on the Fetch standard.
