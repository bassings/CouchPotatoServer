## Problem

Five settings groups are edited as rows but stored as parallel comma-separated
lists, one list per column, paired back up by position when read:

| Section | Columns (`combine`) | Declared in |
|---|---|---|
| `newznab` | `use`, `host`, `api_key`, `extra_score`, `custom_tag` | `couchpotato/core/media/_base/providers/nzb/newznab.py` |
| `torrentpotato` | `use`, `host`, `pass_key`, `name`, `seed_ratio`, `seed_time`, `extra_score` | `couchpotato/core/media/_base/providers/torrent/torrentpotato.py` |
| `imdb`, `itunes`, `letterboxd` automation | `automation_urls_use`, `automation_urls` | `couchpotato/core/media/movie/providers/automation/` |

Three facts make this unsafe, all confirmed in review of PRs #587 and #588:

1. **A comma inside one cell becomes a new position.** Nothing rejects or
   escapes it. For `newznab` and `torrentpotato` the cell next to a host is a
   credential (`api_key`, `pass_key`), so the text after a comma in a URL is
   treated as another indexer and is sent the NEXT row's credential. Reproduced
   on master through the real Settings page and the real `search()` loop.
2. **The page hides the damage and then makes it permanent.** `combinedField`
   (`couchpotato/ui/templates/partials/settings/scripts.html`) builds its rows
   from the longest stored list and, on any edit, re-saves every column padded
   to that length. After a reload and one unrelated edit the lists are equal
   length with hosts shifted against keys. Deleting the bogus row leaves the
   following indexer paired with the wrong key.
3. **The server cannot see rows.** Each column is saved by its own request
   (`settings.save` with `section`, `name`, `value`), debounced separately, and
   the value arrives already joined. The server cannot tell a comma inside a
   cell from a separator, and a failed request leaves the columns from
   different edits side by side. `getParams`
   (`couchpotato/core/helpers/request.py`) also URL-decodes values a second
   time, so `%2C` is stored as a comma.

`getHosts` raises when `use` is shorter than `host`, and `isEnabled` raises on
an empty or non-numeric `use`. Those crashes currently stop a search before
later rows are queried. Two attempts to turn them into "disabled" each produced
a measured case where a credential reached the wrong indexer where master had
stopped (see `docs/technical-debt.md`, "Newznab positional lists"). They are
not to be guarded until misalignment cannot be written in the first place.

A fourth fact was found after the planning cycle: **a writer the first draft
never named, and a wizard button that has been calling a route that does not
exist.**

4. **`jackettSync` writes all seven torrentpotato columns with seven separate
   per-column writes** (`torrentpotato.py:393-399`), with no comma check and
   nothing that undoes the earlier writes if a later one fails. Its live caller
   is the Settings page button: the `jackett_sync` option declares
   `button_action` `torrentpotato.jackett_sync` (`torrentpotato.py:496`), which
   `partials/settings/scripts.html:807` fetches. The wizard's "Sync Trackers
   from Jackett" does not reach it: `wizard.html:1543` requests
   `provider.torrentpotato.jackett_sync`, while the registered route is
   `torrentpotato.jackett_sync` (`torrentpotato.py:29`), and an unregistered
   route returns `API call doesn't exist` (`couchpotato/api.py:55`). The wizard
   E2E specs stub the name the wizard requests, not the registered one
   (`tests/e2e/wizard-keyboard.a11y.spec.ts:235`, `:295`, `:1111`), so the
   suite is green over a button that cannot work against a real server.
   Decision (orchestrator, 2026-11-14, under the owner's standing authority for
   engineering calls): the wizard's URL is corrected only in or after the slice
   that puts `jackettSync` behind the validated group write (P2), never before,
   because correcting it earlier would newly expose the unvalidated writer to
   the first-run screen; the E2E stubs are corrected in the same slice.

## Approach (for the planning cycle to challenge)

The owner's decision is that the server, not only the page, refuses a save
that would put a comma inside a row. Because of fact 3 that cannot be bolted
onto the existing per-column save. The proposal:

- A save of a multi-row group goes to the server **as rows**: one request
  carrying every column of the group, cell by cell.
- The server validates the whole group (every row has the same columns; no
  cell contains a comma; values are taken as sent, not decoded a second time)
  and writes all columns in one operation, or writes nothing.
- The existing per-column `settings.save` is refused for any option that
  belongs to a `combine` group, so there is one way to write these values and
  it is the validated one.
- The Settings page and the setup wizard both use it. The page shows which row
  and which field was refused, and never re-saves columns it merely padded.
- The stored format in `config.ini` does not change. This is a write-path
  change, not a migration.

## Not in scope

- Changing how indexers are stored (records instead of parallel lists). The
  owner chose against it on 2026-11-14: the migration risk sits in the
  irrecoverable tier.
- Detecting or repairing installs whose lists are already misaligned. It
  cannot be done reliably; the v3.278.0 release notes tell users to check.
- Guarding `getHosts` / `isEnabled` (and the same lookups in
  `torrentpotato.py`). A follow-up may revisit them once this has shipped and
  misalignment can no longer be written.
- The second URL-decode in `getParams` for settings outside the combined
  groups. It is recorded as debt; the new save path must not depend on it.
- Preserving a comma inside a stored automation URL. The automation readers
  already split that column on commas (`imdb.py:81-82`, `itunes.py:25-26`,
  `letterboxd.py:38-39`, through `splitString`,
  `couchpotato/core/helpers/variable.py:438-443`), so a stored URL containing
  a comma is already read as two URLs. The page shows it as the rows the
  readers already see and saves it as those rows on the next edit of that
  group, so refusing commas breaks nothing that works today. *(added at the
  spec gate, 2026-11-14; no planning lens wrote it)*

## Acceptance criteria

*Written by `/plan-cycle` on 2026-11-14 from nine lens reports. The outcomes the criteria secure:*

- After this change no sequence of saves through the Settings page, the
  wizard or the settings API can leave a credential paired with a host it was
  not entered against, in any `combine` group, in a case where the save
  reported success.
- A refused save changes nothing on disk and tells the user which row and
  field to fix, without echoing a credential or a URL.
- A save that succeeds for a group is all-or-nothing across its columns.
- Existing aligned groups whose non-pairing columns already have the row
  count (Definitions) read and re-save unchanged, byte for byte. Two aligned
  shapes do change on their first save, and only in these ways: a
  wizard-written newznab group has its surplus default cells in `extra_score`
  and `custom_tag` dropped, and the shipped torrentpotato defaults are padded
  to their two rows. *(narrowed at the second spec gate pass, 2026-11-14)*
- An existing misaligned configuration is not silently "repaired" into a
  different wrong pairing by opening the page.
- Rollback is reverting the commit: the stored format is unchanged.

#### Definitions

*(added after the planning cycle from the consistency review; orchestrator,
2026-11-14, under the owner's standing authority for engineering calls. D2, D3
and every criterion that uses these terms use them in this sense.)*

- **Stored indexer** (Newznab): a stored row with a non-empty `host` AND a
  non-empty `api_key`. A fresh install stores six default hosts with `use` all
  `0` and empty keys: `newznab.py:293-327` declares `enabled` default `True`,
  six hosts, `use` of `0,0,0,0,0,0` and `api_key` of `,,,,,` (the consistency
  review measured `registerDefaults` on an empty config writing exactly those
  values). Those six rows are **not** stored indexers. `isEnabled`
  (`newznab.py:197`) requires a non-empty key, so a keyless row can never be
  searched. A stored row that is not a stored indexer is a *hidden row* for the
  wizard: a keyless shipped default, a user-entered host with no key, or a
  *hostless row* (a key and no host). The wizard does not display hidden rows
  and PRESERVES them: on a save each is written back unchanged at its stored
  position with all its cells (AC-DESIGN-12, AC-PROD-4). *(hidden rows
  preserved, where the first amendment said "not kept": amended at the spec
  gate, 2026-11-14; no planning lens wrote it)*

The four definitions below replace the first amendment's "misaligned group"
paragraph and its row-count sentence. Both gate reviewers measured that rule
against real shapes and it flagged a fresh install, a Settings-configured
install with a key in default row 4, and the shipped iTunes default. *(amended
at the spec gate, 2026-11-14; no planning lens wrote it)*

- **Cells.** A column's cells are its raw stored value split on `,`. An empty
  cell is a position, not a missing one. Nothing is trimmed away or dropped
  when counting. (An empty stored value is therefore one empty cell.)
- **Pairing columns.** For `newznab`: `host`, `api_key`, `use`. For
  `torrentpotato`: `host`, `pass_key`, `use`, `name`. For the automation
  groups: both columns. The other columns (`extra_score`, `custom_tag`,
  `seed_ratio`, `seed_time`) are non-pairing columns. Each group's pairing
  columns are declared once, as a `pairing` list on the provider's `combined`
  option beside `combine`, and `Settings` derives them as it derives the combine
  groups; `group_misaligned(section)` and `group_stored_rows(section)` take no
  column list. The Settings page and the wizard never re-derive alignment in
  script: from P3 the settings read carries each group's misaligned flag computed
  by that one method. *(amended in P2 after review, 2026-11-16)*
- **Misaligned group** (decision D2). Ignore any pairing column whose cells
  are all empty: nothing in it can be mispaired. The group is misaligned when
  the remaining pairing columns do not all have the same cell count. A
  non-pairing column never makes a group misaligned by being shorter, or by
  being longer only by cells that are empty or hold a cell of that column's
  declared default; a non-pairing column longer by a cell holding any other
  value does make the group misaligned, because that cell is data whose row
  cannot be identified. Where a non-pairing column is shorter, the page shows
  that column's declared default for the missing cell and the next successful
  group save writes it. For newznab that is what the reader already supplies
  (`newznab.py:150-154`). For torrentpotato it is not: the reader returns `0`
  for a missing `seed_ratio` or `seed_time` (`torrentpotato.py:149-160`,
  through `tryFloat` and `tryInt`, `couchpotato/core/helpers/variable.py:367-378`),
  not the declared `1` and `40`, so the first save of such a row writes the
  declared defaults where the reader had been using `0`. That is accepted: in
  practice it affects blank rows. *(the torrentpotato statement was amended at
  the second spec gate pass, 2026-11-14)*
  Surplus default cells are not shown as rows and are dropped at the next
  successful group save.
- **Row count.** The largest cell count among the pairing columns, so a stored
  trailing empty row is a row and round-trips. The largest-count rule always
  wins. A group has one row only when every pairing column has a single cell
  (for example a group with nothing stored); torrentpotato's shipped
  `pass_key` of `,` is two cells, so that group has two rows although every
  pairing cell is empty. *(the one-row statement was narrowed at the second
  spec gate pass, 2026-11-14: as first written it conflicted with the
  largest-count rule for that shape)*

Damage that left every pairing column the same length gets no notice: for
example after master's page re-padded the lists following a comma in a URL
(Problem, fact 2). It cannot be detected (Not in scope).

Accepted in the other direction: a healthy pre-#587 wizard group with a
trailing blank row (`host` of `A`, `api_key` of `KA`, `use` of `1,0`) is
classified misaligned. The rule errs toward the notice, and the cost is that
the wizard will not edit Newznab for that install until the rows have been
saved once in Settings. *(recorded at the second spec gate pass, 2026-11-14)*

Proof: request listeners (network and in-page) and the sha256 of `config.ini` unchanged well inside the window, a request at its end (E2E on the fake clock, which keeps running in real time, so the E2E reads inside the window and at its end and the exact boundary is the unit test's, on fake timers: nothing at 7 999 ms, one request at 8 000 ms). (2) **Undo inside the window**, when the removal was the only unsaved change (the group was clean when the row went), cancels the save: no request is ever sent and `config.ini` is byte for byte as it was. When anything else was unsaved, or a save was in flight, Undo restores the row and the normal 500 ms save carries the rows as they now are. (3) **An edit** to another cell of the group in the window, or any further edit, follows the normal 500 ms debounce, carries the removal with it, and ends the line: one request, rows as on screen. A removal made while an earlier edit was still waiting for its own 500 ms moves that edit to the end of the new window; it is carried by the same single request. (4) **A pending removal is never waited on, dropped or stranded.** Everything that sends saves sends it now: `flushPendingSaves` (and so the Trakt authorisation start); a button in the section (Jackett sync: the group is locked, the line goes, and the action's own flush sends the removal before the action; this is the existing lock of AC-DATA-21); Test connection (`testProvider` now saves the section's group first, so the test runs against the rows on screen); and the page going away (`pagehide` sends a pending group save, one waiting on its timer or one queued behind a save already in flight, with `keepalive: true`; nothing waits on the answer). **Leaving the page now sends ANY pending group edit, not only a removal**, a typed cell inside its 500 ms debounce included; the save is the same validated group save, so one the server refuses is refused as before and is lost WITHOUT a message, because nobody is left to read it (the rows are still as stored). Test connection and a button action send a pending edit the same way, and show the refusal if there is one. Proof: unit tests for each path, and E2E for Test connection, the sync and leaving the page (a real navigation inside the real window, `config.ini` read back). (5) **Undo after the window,** when the save has landed or is in flight, restores the row and saves the group through the normal save: one request carrying every row, `config.ini` read back as it was before the removal. (6) **Undo of a removal whose save failed or was refused:** the row is restored and the group is saved again through the normal save. The rows that save carries are the rows the user had on screen before the removal (the restored set), never a set they did not see. If the save failed for a network or server reason the failure message goes with the next verdict (success clears it); if it was refused for another row's comma, the marks move back to their rows (the removed row's own marks are dropped, as at removal) and the next verdict is judged afresh and announced only if it is new. (7) **The line ends** (and Undo is no longer offered) on an edit, an added row, a second removal (which replaces it), the group being locked or its rows being re-read (`replaceGroupRows`), a page reload, and Undo. **The stated limits.** (a) A browser killed, a power cut or a crashed tab during the window loses the pending removal: the row is still there on the next load. That is the safe direction (nothing is deleted that the server was not told to delete), and it is the cost of an undo window. (a2) A phone browser that is backgrounded and then discarded by the operating system may never fire `pagehide` at all (it fires reliably only on a navigation or a close), so the pending removal is lost as in (a): the row is still there on the next load. (b) `pagehide` cannot await a request: if a save for that group is already in flight when the page goes, the keepalive request is sent without waiting for it and the two may land in either order (the older, in-flight request answering last can leave the server with the older rows); the window is a few milliseconds long. A queued save is sent too, and its `queued` flag is deliberately NOT cleared, so if the page survives (a back/forward-cache restore) the in-flight loop sends the rows on screen last and the server ends with what is shown (unit test, the exact sequence). Not covered by a test (the ordering of two requests at unload cannot be driven reliably); the queued-save case is covered by a unit test only. (c) A page restored from the back/forward cache after leaving was not measured. By reading the code the panel comes back as it was, with the removal already sent and Undo still offered; Undo would then save the restored rows through the normal save, which is correct, but nothing tests it. A page that survives `pagehide` also stays marked unsaved (dirty, its timer cleared) after a keepalive save that SUCCEEDED, when no save was in flight; that is harmless (a later save re-sends the same rows) but the automatic refresh of that group does not run until then. **If the keepalive save was REFUSED or failed** (nobody is left to read the answer), a page restored from the cache shows rows the server does not hold, with no mark and no error, and nothing re-sends: the group stays dirty with its timer cleared, and the next edit saves all rows. (d) Another tab: the group save is built from the page's snapshot and overwrites the stored rows wholesale (AC-DATA-4, withdrawn). The window makes the passive exposure longer: a tab's removal reaches the server 8 seconds after the click, where an edit's 500 ms save did so after half a second, so a second tab's change in that gap is overwritten (16 times as long). And Undo, pressed at ANY later time (the line stays), re-saves that page's whole snapshot with the row put back, however many minutes it is since the page last read the settings, overwriting whatever another tab or a Jackett sync stored meanwhile. Nothing detects it (the freshness token is the withdrawn durable fix). Recorded in `docs/technical-debt.md`. Proof: `tests/unit/ui/settings-group-save.spec.ts` ("removing a row, with a way back") and the E2E named in AC-PROD-11 and AC-A11Y-18. Each guard was proven load-bearing by deliberate mutation: the window shortened to 500 ms; Undo restoring at the wrong index; Undo dropping a column; the pending removal left out of `flushPendingGroups`; the line ended by a successful save; a second removal keeping the first; a cell value added to the announcement; the `pagehide` wiring removed; `testProvider`'s flush removed; the lock no longer ending the line.

### Architecture (lens-architecture)

- **AC-ARCH-1:** The map of combine groups (section to ordered column list) comes from one Settings method that reads the `combine` declarations already registered through the `settings.options` event; no production file hard-codes the list of combine sections or their columns a second time. Proof: a unit test registers a synthetic section `zz_test` whose option declares `type: 'combined'` with a `combine` list of use, host and key, and with no production code edited the group save accepts a valid `zz_test` row set and per-column `settings.save` refuses `zz_test.host`; plus a grep for section-name literals. *(merges the synthetic-section clause of AC-QA-7)*
- **AC-ARCH-2:** The per-column refusal in `settings.save` asks the single membership method (`Settings.combine_column`, with `is_combine_option` as its boolean wrapper), matching `optionxform(name.strip())`, so a name with leading or trailing whitespace is matched as the column it would become (AC-SEC-3); the group save takes its columns from `combine_groups()`, the same source, and asks no per-option membership question; grep shows `combine_column` called only from the refusal and the wrapper, and no other `combine` membership test in `couchpotato/core`. Proof: code read plus grep, and a unit test of the membership test over whitespace variants. *(the `strip()` clause was amended at the spec gate, 2026-11-14; no planning lens wrote it)* *(amended in P6 after review, 2026-11-18: the first wording said the refusal and the group save both ask the membership method, and "exactly these two call sites". The group save has no per-option question to ask: it validates whole rows against the columns `combine_groups()` returns. `is_combine_option` has no production caller; it is kept because P1's membership tests and the wizard first-party-writer check call it, and it is a one-line wrapper)*
- **AC-ARCH-3:** Writing a combine group is one method on Settings that validates the whole group, sets every column, calls `self.save()` once and restores the in-memory parser if validation or the write fails; the API view for the new route and `jackettSync` are thin callers of that method and repeat none of its validation; a caller may use the writer's own cell test (`unstorable_cell`) to skip a row, which repeats no rule. *(amended in P2 after review, 2026-11-16)* Proof: code read, with the failure behaviour proven under AC-DATA-1 and the locking under AC-DATA-3.
- **AC-ARCH-5:** The new route is registered with `addApiView` in `Settings.__init__`, next to `settings.save`, with a `docs` entry; the change adds no branch naming the route to `callApiHandler` in `api.py` or to `getParams` and `dictToList` in `request.py`, and any change to the catch-all in `couchpotato/__init__.py` is limited to refusing the wrong method, body type or top-level body keys for a declared set of routes (AC-SEC-2, AC-ARCH-6, AC-ARCH-11(iv)), in the style of `ORIGIN_CHECKED_API_ROUTES`, plus the two route names AC-SEC-9 adds to that constant (`torrentpotato.jackett_sync` and, since the second spec gate pass, 2026-11-14, `torrentpotato.jackett_test`). Proof: diff read. *(amended at synthesis: the lens asked for no catch-all change, which yields to AC-SEC-2; widened at the spec gate, 2026-11-14; no planning lens wrote it, to admit the raw-body key check and the origin-checked route)*
- **AC-ARCH-6:** Rows reach the server as a JSON array of row objects in an `application/json` POST body, the one shape `getParams` passes through without decoding; `rows` delivered any other way (a string, a JSON text in a form field, bracket-keyed form fields such as `rows[0][host]`, or query parameters) is refused with `config.ini` unchanged. Proof: integration tests posting each refused shape. *(the byte-for-byte round-trip is AC-QA-3; replaces the index-gap cases of AC-QA-4 and AC-DATA-5; decision D4)*
- **AC-ARCH-8:** On the Settings page a combine group is one pending save keyed by the group, not one per column, and `flushPendingSaves()` also flushes pending group saves, so nothing that awaits it (such as the OAuth device-code flow) can run ahead of an unsaved group. Proof: Playwright request intercept. *(the request counts are AC-DATA-11 and AC-SEC-10)*
- **AC-ARCH-10:** No new dependency edge: `couchpotato/core/settings.py` imports nothing from `couchpotato.core.media`, `couchpotato.ui` or any provider module, and provider modules declare nothing new beyond their existing `combine` lists. Proof: import-graph grep of the diff.
- **AC-ARCH-11:** Contracts the first slice (P1) freezes, so that later slices can build in parallel against them: (i) one Settings method derives section to ordered columns from the registered options, and one membership test applies the same option-name folding the config parser uses (`optionxform`), the methods AC-ARCH-1 and AC-ARCH-2 name; (ii) the group writer accepts either rows or a builder callable that runs under the lock and returns rows, so a caller can read the existing rows and write in one continuous lock hold (needed by AC-DATA-9) without importing the module-private lock (`_PASSWORD_SAVE_LOCK`, `couchpotato/core/settings.py:28`). A builder only reads and returns rows. The writer snapshots the group's columns before calling it, so a builder's own writes to those columns are undone on any refusal or failure; a builder must never call `save()` (a write to disk cannot be undone) or write outside the group. A builder that raises anything other than `GroupMisaligned` gets the write-failure body of (iii) and one ERROR line naming the section and the exception type, with no traceback and no value *(amended in P1 after review, 2026-11-15)*. The writer returns the object of (iii) to a Python caller and never raises for a refusal. It emits AC-OPS-1's WARNING itself, so `jackettSync` inherits it. It does not raise for a write failure either: it restores the in-memory columns, logs AC-OPS-3's single ERROR line itself (so a Python caller such as `jackettSync` needs no handler of its own and cannot forget one) and returns the write-failure object of (iii); where this differs from AC-OPS-3's "the view catches", this sentence governs and the view only relays the result. The view emits AC-OPS-8's INFO; (iii) Success returns exactly `{"success": true}`. A refusal returns `{"success": false, "error": <fixed text for the first reason, no submitted value>, "invalid": [{"row": int|null, "column": str|null, "reason": code}, ...]}`, listing every offending cell; `row` is the 0-based row as sent. Request-level refusals carry one entry with `row` and `column` null. A `not_writable` entry is column-level: `row` is null and `column` is the declared column name, and there may be several. An `unknown_column` entry carries `column` null, because a caller-supplied name is never echoed *(amended in P1 after review, 2026-11-15)*. The reason codes are exactly ten: `comma`, `control_character`, `not_string`, `not_encodable`, `missing_column`, `unknown_column`, `not_writable`, `unknown_section`, `malformed` and `misaligned`, and a unit test asserts the writer can return no other. `not_encodable` is a cell the file encoding cannot hold (a lone surrogate such as `"\ud800x"`: valid JSON text that fails at the UTF-8 file write), refused in cell validation so that bad input is a WARNING-level refusal and never an ERROR-level write failure; `control_character` would not be honest for it. `misaligned` is the tenth code, added because one refusal needs it: a builder callable of (ii) that declines under the lock because the stored group is misaligned (AC-SEC-9 rule (c)); it is a request-level refusal, and the writer itself never judges alignment of what it is sent. The wizard's own refusals (AC-DATA-19, AC-DATA-20, a misaligned group under AC-DESIGN-12) are decided in the page and send no request, so they need no code. A write failure returns `{"success": false, "error": ...}` with no `invalid`. A transport refusal under (iv) is HTTP 400 with one `malformed` entry; (iv) the transport guard lives in the API dispatch, within the bound AC-ARCH-5 sets: the route is refused unless the request is a POST with an `application/json` body and carries no query parameters other than the API's existing cache-buster (`t`, which `couchpotato/api.py:63` removes). The body's top-level JSON value is an object with exactly the keys `section` and `rows`, checked on the raw body before `getParams` runs, and its `rows` value must be a JSON array whose every element is a JSON object (the shared parser turns an object with numeric-looking keys, such as `{"0": {...}}`, `""`, `"."` or `"1.5"`, into a list, so such a body would otherwise reach the writer looking like rows), a body nested so deeply that parsing raises `RecursionError` is refused as any other malformed body (400, never 500), and the refusal logs one WARNING from the API dispatch that carries no caller text *(amended in P1 after review, 2026-11-15)*: after parsing, a bracket-keyed member inside a JSON body (`"rows[0][host]"`) is indistinguishable from a nested one, and its value is decoded once. Requiring `application/json` is this route's cross-site defence: a cross-site page cannot send that content type without a preflight, and the CORS middleware is built from `cors_origins`, whose default is empty, so no origin is allowed and the preflight is refused (`couchpotato/__init__.py:1242-1255`). A test therefore sends a `text/plain` body holding valid JSON and asserts it is refused with `config.ini` unchanged, so a later relaxation of the content-type rule cannot silently reopen cross-site writes. Proof: unit tests on each of the four, including an extra top-level key, a missing key, a bracket-keyed member and the `text/plain` case. *(added after the planning cycle from the consistency review / delivery plan; no lens wrote it; the top-level-key rule and the cross-site statement and test were amended at the spec gate, 2026-11-14; no planning lens wrote it; the response contract of (iii), the reason codes and the writer's return and logging duties in (ii): amended at the second spec gate pass, 2026-11-14)*
